01先跑起来

脚本在 labs/02-minimal-session/session.mjs， 只用 Node 内置模块，没有依赖。它维护一个内存里的笔记数组，声明一个 notes_add 工具，然后让模型添加一条笔记。

02三段拆解

整个脚本可以拆成三段：传输、生命周期、工具。真正需要你写的只有第三段； 前两段在课程 01的五道接缝里已经出现过。

01

传输：一行一个 JSON，三个分支

有 method 有 id 是反向请求；有 method 无 id 是通知；只有 id 是响应。客户端请求用自增数字，服务端请求用它自己的 id。

session.mjs:80–145
02

生命周期：握手 → 建线程 → 开始一轮

initialize 打开实验能力，thread/start 声明工具， turn/start 发起工作；一个 deferred 在 turn/completed 时结算。

session.mjs:342–430
03

工具：反向请求，本地执行，结果回传

收到 item/tool/call 后调用 runTool，把 { success, contentItems } 按原 id 写回去。失败也是结果。

session.mjs:209–300

传输：三行判断，三种消息

session.mjs · handleLine简化
const hasMethod = typeof message.method === 'string';
const hasId = message.id !== undefined;

if (!hasMethod && hasId) {
  settleResponse(message);          // 我们请求的响应
} else if (hasMethod && hasId) {
  void handleServerRequest(message); // 服务端反向请求
} else if (hasMethod) {
  handleNotification(message);       // 通知，不需要回答
}

这三行就是整个协议的分类器。注意：服务端请求的 id 由 app-server 分配， 第一次是 0；它和我们自己请求的 1、2、3 是两个命名空间。响应时原样回传，不要重新编号。

生命周期：先挂好 deferred，再发 turn

session.mjs · main简化
const done = deferred();
turnDone = done;

await request('turn/start', {
  threadId,
  input: [{ type: 'text', text: PROMPT }],
});

await done.promise;

为什么先挂 deferred？因为 turn/completed 可能在 turn/start 的响应之后立刻到达；如果先 await 响应再挂监听，就会漏掉它。 这和浏览器里「先注册监听，再发请求」是同一个道理。

工具：把 ok 翻译成 success

session.mjs · handleServerRequest简化
const result = runTool(tool, args);

send({
  id: message.id,
  result: {
    success: result.ok,
    contentItems: [
      { type: 'inputText', text: JSON.stringify(result) },
    ],
  },
});

runTool 返回的 { ok, ... } 是业务语义； success 是协议语义。两者之间只隔一层翻译：成功就 success:true，失败就 success:false，但 contentItems 里仍然放完整 JSON，让模型读得到原因。

记住这个形状

工具结果永远是 { success, contentItems }； 业务结果永远放在 contentItems[0].text 的 JSON 里。 前者给协议，后者给模型。

03读输出：三个对照

回到你的终端输出，找这三组关系。先自己想，再展开对答案。

  1. threadId 出现在哪些消息里？ 它是这一轮所有事件的归属；turn/start、item/*、turn/completed 都带它。
  2. callId 把哪几条消息串起来？ item/started、item/tool/call、item/completed 共享同一个 callId。
  3. 为什么响应 id 是 0？ 因为服务端请求的 id 就是 0；原样回传。它不是客户端的自增序号。
展开：一条工具调用的完整关联 
item/started       callId=call_00_...      status=running
item/tool/call     callId=call_00_...      arguments={text:"..."}
item/completed     callId=call_00_...      status=ok

turn/start         turn.id=tu_...          status=inProgress
turn/completed     turn.id=tu_...          status=completed

工具事件回答「做了什么」，turn 事件回答「这一轮有没有结束」。 它们是两条线，不要用 item/completed 去结算整个轮次。

05改一改：给笔记加一个 mood

现在轮到你改代码。目标：让工具多一个 mood 字段，取值为 calm 或 urgent，并且要求模型必须传。做完后重跑，你应该在 arguments 里看到它。

  1. 改 schema：把它变成必填 在 NOTES_ADD_TOOL.inputSchema.properties 里加 mood，并把 required 改成 ["text","mood"]。
  2. 改执行：校验并保存 在 runTool 里只接受 calm / urgent；其它值返回 {ok:false, code:'invalid_arguments'}。
  3. 改 prompt：明确要求 把 PROMPT 改成「添加一条 mood 为 calm 的笔记……」，重跑。
  4. 看反馈 如果模型漏传，它会收到 invalid_arguments 并重试；如果它改对了，arguments 里会出现 mood。
展开：参考改动（先自己写，再看）
schemasession.mjs
mood: {
  type: 'string',
  enum: ['calm', 'urgent'],
  description: 'How the note feels. Required.',
},
// ...
required: ['text', 'mood'],
runToolsession.mjs
const mood = args?.mood;

if (mood !== 'calm' && mood !== 'urgent') {
  return {
    ok: false,
    code: 'invalid_arguments',
    message: 'mood 必须是 calm 或 urgent',
  };
}

const note = {
  id: `note_${notes.length + 1}`,
  text,
  mood,
  createdAt: new Date().toISOString(),
};

promptsession.mjs
请调用 notes_add，添加一条 mood 为 calm、
内容为“第二次运行”的笔记，然后告诉我总数。
这一步的反馈从哪来

不是靠肉眼猜，而是靠模型的行为：它要么按 schema 传参，要么收到 invalid_arguments 后重试。你要观察的是 arguments 和 item/completed 的 status，而不是最终那句漂亮话。

06迁移：只保留骨架，换掉工具

这个 lab 里，和「笔记」绑定的只有四处：NOTES_ADD_TOOL、 runTool、notes 数组、PROMPT。 其余部分——进程、JSONL、id 对齐、deferred、结果翻译——原样搬到你的项目。

  • 第一个工具选什么？选一个「读」或一个最小的「写」，不要一上来做完整 CRUD。
  • 它返回什么？新状态 + 新版本号；失败时返回 code 与 message。
  • 哪个动作不可逆？先不做，等课程 04 的确认通道；lab 阶段只做可撤销的写入。

课程 03 会把 notes_add 放大成一套工具集：schema 怎么收紧、失败码怎么设计、 expectedRevision 怎么防覆盖、为什么工具要串行执行。
