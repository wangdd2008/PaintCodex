课程 01 / 把 Codex 变成引擎

一条消息的旅程：从 codex exec 到 app-server

你已经会用 Codex CLI：给一段话，拿回一段文本。PaintCodex 的 AI 却能读画布、改图层、发现冲突后重读。 差别不在提示词，而在谁替模型执行动作，结果又怎么回到模型。

约 12 分钟 1 条交互消息流 4 道检索题 基线 codex-cli 0.164.0

本课结束时，你能

  • 用自己的话说清 进程 / 线程 / 轮次 / 条目 四者的关系；
  • 在五道接缝里，指出任意一条消息由谁处理、坏了会怎样；
  • 判断一条消息是请求、响应还是通知，以及它该不该带 id。

01先换一个心智模型

codex exec 的模型是「一次调用 = 一次问答」：进程起来，读提示词，输出文本，进程结束。 它很适合批处理，但模型在里面没有手——它只能说话，不能读你的状态，也看不到自己上一句造成了什么。

app-server 的模型是「一个长驻进程 = 多条线程；一条线程 = 多轮；一轮 = 多次工具调用」。 模型仍然不能直接改你的数据；它只能请求宿主执行一个在建立线程时就声明好的工具。 宿主执行完，把结果作为一条消息送回模型，模型再决定下一步。

那为什么不继续用 exec？ 因为它的交互是单向的：模型只能输出文本，宿主只能在事后解析。SDK 把这条路线包得更顺手， 但仍然没有「服务端反向请求客户端执行函数」这一层。自建 function calling 直连模型 API 也能做到， 代价是丢掉本地 Codex 的会话、沙箱与模型接入。三条路的差别不在提示词，而在谁能发起工具调用：

  • codex exec / SDK：一次性运行，输出事件流；模型不能回调你进程内的函数，适合「让 Codex 在仓库里干活」。
  • 自建 function calling：直连模型 API，工具回路全部自己写；适合云端产品，但要自己补会话、沙箱、取消与重试。
  • app-server + dynamic tools：长驻进程、thread/turn、反向工具请求；代价是 experimental 协议与一套要自己维护的状态机。
一句话

模型没有手。手是宿主进程在 thread/start 时声明的 dynamic tools； 每个工具都在宿主进程内执行，结果再回到模型。集成工作的大半，就是在维护这条回路。

进程 process
长驻的 codex app-server 子进程。一个 daemon 一个，承载协议与模型连接；崩了，下一次对话时再懒启动。
线程 thread
一段持久对话，一条画布一条。它携带记忆，让「刚才那个圆」在下一句话里仍然指代得清楚。
轮次 turn
一条用户消息引发的工作。可以包含多次工具调用，直到 completed、failed 或 interrupted。
条目 item
轮次里的事件单位：一条助手消息、一次工具调用、一次命令执行。用 item/started 与 item/completed 观察。

thread 不是 UI 里的「会话列表」，而是模型侧的上下文容器。删掉 thread，指代关系就没了； 但画布数据仍在你的数据库里——这两件事必须分开想。

initialize：打开实验能力

→ {"id":1,"method":"initialize","params":{
     "clientInfo":{"name":"paintcodex","version":"0.1.0"},

← {"id":1,"result":{"userAgent":"...","platformFamily":"..."}}

为什么：experimentalApi 是声明 dynamic tools 的前置开关，缺了它 thread/start 会被拒。进程是懒启动的：daemon 启动时只跑 codex --version 闸门， 第一次对话才 spawn。

daemon → app-server · 请求 step 04

thread/start：把画布交给模型

→ {"id":2,"method":"thread/start","params":{
     "cwd":"...",
     "sandbox":"read-only",
     "approvalPolicy":"never",
     "ephemeral":false,
     "dynamicTools":[
       {"type":"function","name":"canvas_get_context",
        "description":"...","inputSchema":{...}}
     ]}}

← {"id":2,"result":{"thread":{"id":"th_9c1e"}}}

为什么：工具在建立线程时声明一次，随线程持久化；模型能做的，恰好就是这张表里的。 read-only 不是不信任模型，而是它不需要 shell：唯一的写入口就是你的工具。

→ {"id":3,"method":"turn/start","params":{

← {"id":3,"result":{"turn":{"id":"tu_4b2a"}}}

为什么：runtime 把这个 turn 登记进 activeTurns。之后每一条事件都带 threadId，靠它找回对应的回调与取消信号。

← {"method":"item/agentMessage/delta","params":{

为什么：文本只是事件流的一种。它用来降低等待焦虑，不用来判定 turn 结束； 模型可能说完一句又去调工具。

app-server → daemon · 反向请求 step 07

item/tool/call：这就是「手」

← {"id":"srv_1","method":"item/tool/call","params":{
     "threadId":"th_9c1e","turnId":"tu_4b2a",
     "callId":"call_1","namespace":null,
     "tool":"canvas_get_context",
     "arguments":{"canvasId":"cv_7f3a"}}}

为什么：方向反过来了：服务端请客户端执行。这个请求必须被回答——不回答， 模型会永远等下去；回答错了，它会基于错的事实继续画。

tools.ts · declarations
daemon · 本地执行 step 08

校验 → 读状态 / 走 dispatcher

tools.execute("canvas_get_context", args, ctx)
  └─ service.getCanvas("cv_7f3a")
     → { ok: true,
         canvas: { id, revision: 7, ... },
         layers: [{ id: "ly_1", name: "红日", ... }] }

为什么：工具就在 daemon 进程里，没有跨进程序列化。写类工具不会自己改数据库， 而是调用 dispatcher.dispatch()，和人类写入走同一条状态机。

tools.ts · dispatchTool
daemon → app-server · 响应 step 09

成功和失败，都是结果

→ {"id":"srv_1","result":{
     "success":true,
     "contentItems":[
       {"type":"inputText","text":"{\"ok\":true,\"layers\":[...]}"}
     ]}}

为什么：失败会变成 {"success":false} 加一段可读 JSON，例如 revision_conflict 附带 currentRevision。模型因此能看见自己错了， 重读再试；反过来，静默重试会让它永远学不会。

codex-runtime.ts · buildToolResponse
app-server → daemon · 通知 step 10

turn/completed：结算 Promise

← {"method":"item/completed","params":{
     ..., "item":{"type":"dynamicToolCall","id":"call_1",

← {"method":"turn/completed","params":{
     "threadId":"th_9c1e",
     "turn":{"id":"tu_4b2a","status":"completed"}}}

为什么：工具 UI 帧与 turn 生命周期是两条线：前者让用户看到「动了什么」， 后者才让 startTurn 的 Promise 结算。状态也可能是 failed 或 interrupted，调用方要分别处理。

04三个判断，迁移时照抄

这条链路里真正需要动脑的，不是 JSON 怎么拼，而是三个取舍。它们在 PaintCodex 里都有明确的 反面教材；换成你的领域，结论仍然成立。

上下文：拉，不推

提示词只放「身份 + 版本 + 摘要」。细节通过一个只读的 *_get_context 工具现场拉。 推送的快照会过期，而且随对象规模膨胀；拉取永远新鲜，代价只是多一次工具调用。

失败：结果，不是异常

工具失败返回 { ok: false, code, message }，由宿主翻成 success: false 送回模型。 不要替模型重试、不要静默吞掉；一个看不见自己失败的执行器，不可能自纠。

并发：单写者，版本校验

同一线程的工具调用串行执行；写操作带 expectedRevision，不匹配就返回 revision_conflict，让模型重读。两个写并发不是「更快」，是互相覆盖。

先记住这一条

工具越少，模型越不容易选错。一个读工具 + 少量写工具，通常比「把 API 全暴露」更可靠。

06迁移到你的项目

在写下第一行集成代码之前，先回答三个问题。它们决定工具集，而工具集决定模型能做成什么。 下一课我们会用你的答案设计一个最小工具集。

  1. 你的领域对象是什么？ 给它一个 id、一个 revision、一份摘要。提示词只需要这三样；细节用一个只读工具现场拉。
  2. 用户语言里的动词，哪些必须成为工具？ 读一个，写按动词拆；每个写工具都返回新的 revision。别把内部 API 全暴露，工具越少越可靠。
  3. 哪个动作不可逆？ 删除、发送、付款、覆盖发布走确认；可撤销的新建与改写直接做。确认属于你的工具层，不属于 Codex 的审批策略。

这三问的答案写进你的笔记；下一课开场我会先问它们。
