# 01 · 首次进入、画布与画笔体验审计

**Status:** draft

**审计人:** Alex（产品经理）

**日期:** 2026-10-26

**审计对象:** PaintCodex Phase 1 单画布工作区：首次进入、空状态、新建画布、画笔、撤销/重做副作用、自动下载、导出与刷新持久化

**证据来源:** `.scratch/product-audit/evidence/01-first-run.md`、`02-canvas-brush.md`、`03-layers.md`、`04-ai-chat.md`、`05-export-persistence.md`、`07-cross-cutting.md`；`.scratch/phase-1-mvp/spec.md`；`apps/web/src/app/App.tsx`、`features/canvas/CanvasStage.tsx`、`services/canvas-store.ts`、`services/json-export.ts`、`services/png-export.ts`、`features/layer-panel/LayerPanel.tsx`

**限制:** 我没有浏览器执行权限，未做真实用户访谈，也没有行为数据。下文所有“用户影响”均标注为假设；工作量是 PM 粗估，需工程用 T 恤码复核。

> **结论先行：** 服务端持久化本身是可靠的——画布、图层、刷新恢复、多标签同步都通过了现场验证。真正的问题在前端给出了三个错误信号：**没有画布时画布看起来能画、状态栏写 100% 但实际 44.8%、每 30 秒把“导出”当成“保存”**。三者叠加，会让第一次使用的人得出“这个应用坏了”的结论。

## 1. 审计范围

### 本轮覆盖

- 首次进入、无画布空状态、未建画布就画/聊天。
- 新建画布、画布名称与身份、画布切换后的可达性。
- 画笔基础交互、笔宽/颜色、画布显示比例与状态栏。
- 撤销/重做可用性，以及删除图层后新笔画命名的副作用。
- 自动下载、手动导出、刷新持久化、导出文件命名。
- 与上述路径直接相关的状态反馈（保存、缩放、画布提示）。

### 不在本文件

- AI 对话质量、流式步骤、取消与对话持久化（归 `04-ai-chat` 审计）。
- 图层面板的可见性、删除、目标尺寸、键盘可达性（归 `03-layers` 审计）。
- 监控页、日志分页、AI 成功率口径（归 `06-monitor`）。
- 响应式、全局可访问性、`<html lang>`、全局本地化（归 `07-cross-cutting`）。
- Phase 1 明确排除项：`.aipaint`、形状/文字/橡皮/填充、图层重排与合并、AI 操作确认、Electron、服务端 PNG 导出。

### 与 spec / ADR 的关系

- 本文件结论不与 ADR 冲突。自动下载没有 ADR 或 spec 依据，是实现遗留；移除它不改变 `ADR-0003` 的快照撤销，也不改变 `ADR-0005` 的客户端 PNG 导出。
- 画布重命名需要新增一个 `PATCH /paint/canvas/:id`。spec 的 Canvas API 只列了 `POST` 与 `GET`，这是 **spec 缺口**，不是架构重开；数据模型已有 `name` 字段。
- 画笔颜色/粗细不在 Phase 1 的排除清单里。若工程认为它超出“basic brush”，可以降级到 P2，但我建议本轮至少做“颜色 + 粗细”两个最小控件。

## 2. 体验路径摘要

| # | 现场动作 | 实际结果 | 判断 |
|---|---|---|---|
| 1 | 首次打开，无 `canvasId`、无 localStorage | 画布区已渲染 1920×1080 白画布；唯一「新建画布」在右上角；提示为英文 `Blank 1920 × 1080 canvas`；图层面板写「尚未加载画布。」；AI 输入框可用 | 假画布 + 弱引导 |
| 2 | 未建画布，点「画笔」拖一条线，等 800ms | `layers: 0`、`nonWhitePixels: 0`、`undoDisabled: true`，无错误 | 笔画被静默丢弃 |

| 5 | 画 7 条线 | 图层 `Stroke 1`…`Stroke 8`；固定 `#111111`、宽度 `4`；屏幕上约 1.8px | 可用，但创作控制缺失 |

| 7 | 停笔等待 33 秒 | 拦截到 1 次下载：`Untitled.json`；代码为 `setInterval(..., 30_000)` | 假保存 + 文件污染 |
| 8 | 点「导出 PNG」「导出 JSON」 | `Untitled.png`、`Untitled.json`；无成功反馈 | 文件不可区分 |
| 9 | 再点「新建画布」 | 无确认；URL 和 localStorage 被 `replaceState` 覆盖；`history.back()` 直接离开应用 | 旧画布从 UI 不可达 |

## 4. 发现详情

### F-01 无画布时画布仍可交互，笔画被静默丢弃

**严重度:** P0 · **工作量:** S · **置信度:** 95% · **类型:** 缺陷 / 首次体验阻断

**现场证据**

- 无画布时，可访问性树仍包含一张 1920×1080 的画布；「画笔」「选择」可用，撤销/重做禁用。
- 在画布上拖出一条线，等待 800ms 后：`layers: 0`、`nonWhitePixels: 0`、`error: null`、`undoDisabled: true`。
- `CanvasStage.tsx` 的 `handlePathCreated` 在 `!current` 时直接 `canvas.remove(path)`，没有提示、没有保存、没有引导。
- 画布、画笔按钮、AI 输入框三者都“看起来可用”，但只有 AI 能返回文本，无法真正落图层。

**用户影响（假设，无访谈/无行为数据）**

第一次打开的用户很可能会先画一笔试试。笔画消失后，他不会认为“我还没建画布”，而会认为“浏览器/触控/这个应用不支持画图”。这是典型的第一会话流失点，也会直接污染用户对后续 AI 能力的信任。

**建议**

1. 无画布时禁止进入绘制模式：`isDrawingMode = false`，画笔和选择按钮禁用，并在点击时给出明确提示「请先新建画布」。
2. 画布区不要再渲染可交互的“假画布”。可以保留白色背景作为视觉底，但必须覆盖空状态层，或至少设置 `pointer-events: none`，让用户无法在无文档时产生路径。
3. 在 `handlePathCreated` 保留防御性 guard：没有 canvas 时不创建图层，但要有用户可见提示，而不是 `remove` 后静默结束。
4. AI 输入框在无画布时禁用，placeholder 改为「先新建画布，再让 AI 作画」；不要允许 AI 回复“我可以添加图层”却没有承载对象。

**验收标准**

- Given 无画布，when 用户点击画笔或画布，then 画笔按钮为 disabled，画布不产生路径，不发任何 `POST /paint/canvas/:id/layers` 请求。
- Given 无画布，when 用户查看画布区，then 看到居中的「新建画布」主 CTA，而不是可交互的白色画布。
- Given 已有画布，when 用户画第一笔，then 正常创建 `Stroke 1` 并出现在图层面板。
- Given daemon 不可用/加载失败，when 用户进入页面，then 看到「无法连接本地服务」与重试/新建入口，而不是一张可以画但画不出东西的白画布。

**备注**

这是本文件唯一的确定性 P0：不依赖网络失败或边界操作，任何首次用户只要先画一笔就会触发。

### F-02 空状态没有主 CTA，文案把“没有画布”说成“尚未加载”，AI 提前承诺作画

**严重度:** P1 · **工作量:** M · **置信度:** 90% · **类型:** 首次体验 / 信息架构

**现场证据**

- 无画布时，唯一创建入口是右上角菜单栏的「新建画布」，与「导出 PNG」「导出 JSON」「监控」并列。
- 画布下方提示为英文：`Blank 1920 × 1080 canvas`。
- 图层面板空状态：`尚未加载画布。`——它暗示“正在加载”，而不是“还没有画布”。
- AI 输入框可用；发送「你好」后 AI 回复“想聊天，还是让我在画布上添加一层新的矢量图形？”，但没有画布可承载图层。
- 画布区没有「新建画布」按钮，也没有解释“画布 / 图层 / AI 生成图层”三者关系。

**用户影响（假设，无访谈/无行为数据）**

- 首次用户需要自己把视线移到右上角，才能找到唯一入口；如果他从画布区开始探索，会先遇到一张假画布。
- “尚未加载画布”会让用户等待一个不会发生的加载，而不是采取行动。
- AI 的承诺提高了预期，但用户继续要求作画时没有承载目标，容易产生“AI 在骗我”的感受。

**建议**

1. 在画布区放置唯一的主 CTA：标题「开始一张画布」，副文案「1920 × 1080，画完后可以让 AI 添加图层」，按钮「新建画布」。右上角按钮保留为次入口即可。
2. 图层面板空状态改为「还没有画布，先新建一张」，并提供一个文本按钮或指向画布区 CTA，不要只说“尚未加载”。
3. 无画布时 AI 输入框禁用，并显示「新建画布后即可让 AI 作画」；不要允许空承诺。
4. 加载失败与无画布要区分：404 / daemon 离线时显示「画布不存在或无法连接本地服务」+「重试」+「新建画布」，不要把错误藏在菜单栏 12px 红字里。
5. 本文件范围内的英文文案统一为中文：`Blank 1920 × 1080 canvas`、`Untitled`。全局 `<html lang="en">` 与 `vector` 等术语归 `07-cross-cutting`，不在这里重复修。

**验收标准**

- Given 无画布，when 用户进入画布页，then 画布区存在唯一主按钮「新建画布」，可键盘聚焦，点击后创建画布并进入可绘制状态。
- Given 无画布，when 用户查看图层面板，then 文案为「还没有画布」，不出现“尚未加载”。
- Given 无画布，when 用户查看 AI 面板，then 输入框 disabled，并显示「先新建画布」的原因。
- Given 画布加载 404/daemon 离线，when 页面渲染，then 显示错误说明、重试和新建入口，不显示可交互白画布。
- Given 首次进入，then 页面中不出现 `Blank 1920 × 1080 canvas` 和 `Untitled`。

**备注**

不建议本轮做“自动创建画布”。它会把“首次访问”变成一次写操作，也会让“新建画布”语义变模糊；先用显式 CTA 验证首次转化。若后续数据显示用户仍在空状态流失，再考虑自动创建。

### F-03 每 30 秒把导出当保存，持续下载 `Untitled.json`

**严重度:** P1 · **工作量:** S · **置信度:** 95% · **类型:** 行为缺陷 / 信任破坏

**现场证据**

- `App.tsx` 中存在：
  ```ts
  // Auto-save: export JSON every 30 seconds when a canvas is active
  const interval = window.setInterval(() => {
    downloadCanvasJson(canvas, canvasJsonFilename(canvas.name));
  }, 30_000);
  ```
- 现场新建画布后等待 33 秒，拦截 `HTMLAnchorElement.prototype.click` 得到：`{ "downloads": 1, "name": "Untitled" }`。
- 该 effect 依赖 `[canvas]`，而每次画布状态变化都会替换 `canvas` 对象，所以定时器会在最后一次修改后重新开始；按 `setInterval` 语义，停笔 30 秒后开始重复下载，而不是只下载一次。现场只验证了第 1 次，重复次数需在真实 Chrome 中复核。
- 服务端本身在每次 mutation 后持久化；刷新后画布与图层都在。自动下载不承担持久化职责。
- 下载通过 anchor 触发；`downloadCanvasJson` 的 `try/catch` 只能捕获序列化错误，捕获不到浏览器拦截下载或用户取消。

**用户影响（假设，无访谈/无行为数据）**

- 用户停笔画画后，Downloads 文件夹会不断出现 `Untitled.json`；如果浏览器询问下载位置或多文件下载权限，会直接打断绘画。
- 用户会把“自动下载了一个 JSON”理解为“保存了”，但这个文件没有导入入口，不能恢复，也不能区分版本。
- 所有文件都叫 `Untitled.json`，浏览器会自动加 `(1)`、`(2)`，用户无法知道哪个是最后版本。

**建议**

明确判断：**这不是可接受的备份，应该直接移除。** 备份至少需要“可恢复、可定位、可版本化”，当前三个都不满足；而服务端持久化已经覆盖了“保存”。

1. 删除 `App.tsx` 中 30 秒自动下载 effect。
2. 用 F-09 的保存状态替代它：保存中 / 已保存 / 保存失败可重试。
3. 手动「导出 JSON」保留为显式备份，并在按钮文案或 tooltip 标注「备份，暂不支持导入」。
4. 如果未来确实需要本地自动备份，使用 File System Access API 或 IndexedDB，并要求用户显式选择目录/开启；不要用 anchor 静默下载。

**验收标准**

- Given 有画布，when 用户停笔 5 分钟不操作，then 不产生任何自动下载，`HTMLAnchorElement.prototype.click` 计数为 0。
- Given 用户画一笔，when 服务端保存成功，then 状态栏显示「保存中…」→「已保存」，而不是触发下载。
- Given 用户点击「导出 JSON」，then 只产生一次显式下载，并有明确反馈。
- Given 浏览器拦截下载，then 用户能看到「下载可能被浏览器拦截」的提示，而不是静默失败。

### F-04 新建画布无确认、`replaceState` 覆盖，旧画布从 UI 不可达

**严重度:** P1 · **工作量:** M · **置信度:** 85% · **类型:** 数据可达性 / 误操作

**现场证据**

- 当前 URL `?canvasId=ffbd57e5-...`，localStorage 同 id，`history.length=2`。
- 点击「新建画布」没有确认弹窗；URL 变为 `?canvasId=247c67e1-...`，localStorage 变为新 id，`history.length` 仍为 2。
- `history.back()` 直接离开应用，没有回到旧画布。
- `canvas-store.ts` 的 `rememberCanvas` 使用 `window.history.replaceState`，且 localStorage 只保存一个 `paintcodex.canvasId`。
- 旧画布仍存在于 SQLite，但 UI 没有“最近画布”或“打开画布”入口；除非用户手动保存过旧 URL，否则无法找回。

**用户影响（假设，无访谈/无行为数据）**

- 「新建画布」和「导出 PNG」「导出 JSON」「监控」并排，误点成本很低；误点后没有确认，旧画布立刻从界面消失。
- 用户会认为“我的画被删了”，虽然数据还在本地数据库，但没有任何可见恢复路径。
- 这是产品感知上的数据丢失，比真正的删除更伤信任；也会制造“能不能帮我找回”的支持成本。

**建议**

本轮不做画布列表/画廊，但必须做两层最小保护：

1. **确认**：当前有画布时，点击「新建画布」弹出确认，说明“当前画布会保留在本地，但将从界面移除；可先导出备份”。取消不改变 URL、localStorage 或当前画布。
2. **单级回退**：提供“返回上一张画布”，不是多条目列表。两种实现任选：
   - 方案 A：新建时把旧 id 存为 `paintcodex.previousCanvasId`，菜单出现「返回上一张画布」；返回后清空该记录。
   - 方案 B：新建画布用 `pushState` 写入新 id，并让 `popstate` 读取 URL 中的 `canvasId` 重新加载；浏览器后退即可回到旧画布。
3. 无论选哪种，新建失败时不能覆盖旧 id；只有创建成功后才更新 localStorage。
4. 画布列表、画廊、多画布管理作为后续建议，不进入本轮范围。

**验收标准**

- Given 画布 A 有图层，when 点击「新建画布」，then 先出现确认；取消后仍是 A，URL/localStorage 不变。
- Given 确认新建为 B，when 用户点击「返回上一张画布」（或浏览器后退），then 回到 A，A 的图层完整、可继续画。
- Given 新建请求失败，when 错误返回，then 当前画布 A 仍可用，localStorage 仍指向 A。
- Given 用户从未新建过第二张画布，then 不显示「返回上一张画布」，避免空入口。

**备注**

这是“访问权丢失”，不是“数据删除”；文案不要吓用户说“会删除”。但也不能因为数据还在数据库就认为无需修——用户找不回来，就等于丢了。

### F-05 所有画布都叫 `Untitled`，不能重命名，导出文件互相覆盖

**严重度:** P1 · **工作量:** M · **置信度:** 90% · **类型:** 画布身份 / 导出可用性

**现场证据**

- 新建画布后名称固定 `Untitled`；菜单栏中是 `<span class="document-name">`，没有点击编辑、铅笔图标或双击重命名。
- 画布名称同时出现在菜单栏、画布下方 hint、图层面板语境中。
- 导出文件名为 `Untitled.png`、`Untitled.json`；文件名来自 `canvas.name`。
- `POST /paint/canvas` 的服务端实现接受 `input.name`，但 Web 端 `createCanvas()` 没有传；也没有 `PATCH /paint/canvas/:id` 路由。
- `png-export.ts` / `json-export.ts` 会清洗非法字符，但不会补充时间戳或唯一后缀。

**用户影响（假设，无访谈/无行为数据）**

- 用户画了多张画布后，所有导出文件都叫 `Untitled`，浏览器自动加 `(1)`、`(2)`；分享或归档时无法判断哪张是哪张。
- 用户无法给画布起名，也就无法在心理上“拥有”这张画布；这对创作工具是身份缺失。
- 导出文件重名会让用户覆盖旧文件，或把错误的版本发给别人。

**建议**

分两步，先做无 API 的快速缓解，再做完整重命名：

1. **快速缓解（S）**：创建画布时传入唯一默认名，例如 `未命名 2026-10-26 14:32`；导出文件名带同一时间戳。这样即使没有重命名 UI，也不会所有文件都叫 `Untitled`。
2. **完整方案（M）**：菜单栏画布名支持双击/铅笔进入 inline edit，Enter 保存、Esc 取消、失焦保存；新增 `PATCH /paint/canvas/:id` 只更新 `name`，返回更新后的 `CanvasDocument`。失败时回滚显示并提示。
3. 导出文件名使用清洗后的画布名；若用户重命名，导出立即使用新名。允许两张画布同名，但文件名补时间戳，避免覆盖。
4. 创建时也可以让用户直接命名，但不要把它做成阻塞式弹窗；默认名 + 可后续重命名更适合快速开始。

**验收标准**

- Given 新建画布，then 名称不是裸 `Untitled`，而是带日期/时间的可读默认名。
- Given 用户把画布重命名为「红色练习」，then 菜单栏、页面标题/提示、导出文件名都使用「红色练习」，刷新后仍保留。
- Given 两张画布都叫「红色练习」，when 分别导出，then 文件名可区分（含时间戳或短 id），不静默覆盖。
- Given 重命名请求失败，then 名称回滚到原值并显示错误，不出现“界面改了但服务端没改”的假成功。
- Given 键盘用户，then 可以通过 Tab 聚焦名称并进入编辑，不依赖双击。

**备注**

需要补 spec 的 Canvas API 一行：`PATCH /paint/canvas/:id`（仅 `name`）。这不是新模块，也不改数据模型；如果本轮不做后端，则至少完成快速缓解，避免所有导出都叫 `Untitled`。

### F-06 删除中间图层后新笔画重名，出现两个 `Stroke 8`

**严重度:** P1 · **工作量:** S · **置信度:** 95% · **类型:** 缺陷 / 误删除风险

**现场证据**

- 现场画到 `Stroke 8`，删除中间的 `Stroke 4`，再画一条，图层名为：
  ```json
  ["Stroke 1","Stroke 2","Stroke 3","Stroke 5","Stroke 6","Stroke 7","Stroke 8","Stroke 8"]
  ```
- `CanvasStage.tsx` 使用 `current.layers.length + 1` 命名；删除任意一层后，长度回退，下一次命名就会与现有最大编号冲突。
- 图层面板、删除确认 `删除图层 "Stroke 8"?`、无障碍名称都会出现两个 `Stroke 8`。

**用户影响（假设，无访谈/无行为数据）**

- 用户看到两个同名图层，无法判断哪个是刚画的；删除确认也只说 `Stroke 8`，容易删错。
- 删错后只能依赖撤销；而快照撤销保留最近 20 个状态，用户未必知道可以恢复。
- 多标签同时画时，`length + 1` 也可能与其他标签的命名冲突；现场未复现，但逻辑上存在。

**建议**

1. 命名改为“当前画布内已有 `Stroke N` 的最大 N + 1”，而不是 `layers.length + 1`。
2. 或者使用每画布单调递增计数器；但不要为此新增数据库字段，优先从现有图层名推导，避免迁移。
3. AI 生成图层如果需要自动命名，也做同画布去重；现场未观察到 AI 重名，先不扩大承诺。
4. 删除确认和无障碍名称在极端重名时补充图层 id 短码或位置，作为兜底。

**验收标准**

- Given 已有 `Stroke 1`…`Stroke 8`，when 删除 `Stroke 4` 后再画一条，then 新图层为 `Stroke 9`，列表中无重名。
- Given 刷新页面，when 再画一条，then 继续使用下一个未占用编号，不回退。
- Given 用户手动重命名过图层，when 自动命名，then 不误解析非 `Stroke N` 名称，仍能给出唯一名称。
- Given 图层重名，when 点击删除，then 确认文案能区分目标（名称 + 短 id 或序号）。

### F-07 状态栏硬编码「缩放: 100%」，实际显示比例 44.8%

**严重度:** P1 · **工作量:** S · **置信度:** 95% · **类型:** 信息失真

**现场证据**

- 同一时刻读取：
  ```json
  {
    "viewport": [1264, 625],
    "canvasScreen": { "x": 81, "y": 69, "w": 858, "h": 481.75 },
    "scale": 0.4479166666666667,
    "status": ["1920 × 1080", "缩放: 100%", "画笔"]
  }
  ```
- 实际显示比例约 **44.8%**（858 / 1920），状态栏仍写 **100%**。
- `App.tsx` 中该值是硬编码字符串，不是真实缩放；画布通过 CSS 适应容器，Fabric 内部坐标仍是 1920。

**用户影响（假设，无访谈/无行为数据）**

- 用户以为自己在 100% 比例下作画，实际看到的是缩略图；对笔宽、构图、细节判断都会偏差。
- 画笔内部宽度 4 在屏幕上约 1.8px，用户会觉得“笔太细”，但状态栏又告诉他 100%，无法建立正确预期。
- 导出 PNG 是 1920×1080，屏幕看到的是 858×481.75；如果用户按屏幕比例估算导出效果，会得到错误预期。

**建议**

1. 计算真实显示比例：`canvasScreen.width / canvas.width`，用 `ResizeObserver` 或 Fabric viewport 的实际缩放；不要硬编码。
2. 状态栏显示「适应窗口 45%」或「缩放 45%」；如果本轮不做缩放控件，明确写“适应窗口”，不要写“100%”。
3. 如果未来加缩放控件，再区分“适应窗口 / 100% / 自定义”；本轮只修显示，不扩大成完整 viewport 功能。
4. 画笔粗细预览也应基于显示比例，避免“选了 4，屏幕上像 1.8”的认知落差。

**验收标准**

- Given 视口 1264×625、画布 1920×1080，when 页面稳定，then 状态栏显示 44.8% ±1%，与 `canvasScreen.width / 1920` 一致。
- Given 用户调整窗口大小，then 比例实时更新，不出现固定 100%。
- Given 代码中不再存在硬编码的 `缩放: 100%`，then 单元测试覆盖比例格式化（四舍五入、整数/小数）。
- Given 本轮没有缩放控件，then 状态栏使用「适应窗口」措辞，不暗示用户可以选择 100%。

### F-08 画笔固定 `#111111` / 宽度 `4`，屏幕约 1.8px，缺少颜色与粗细控制

**严重度:** P1 · **工作量:** M · **置信度:** 85% · **类型:** 创作能力 / 现有能力未 surfaced

**现场证据**

- `CanvasStage.tsx` 中：
  ```ts
  const BRUSH_COLOR = '#111111';
  const BRUSH_WIDTH = 4;
  ```
- 连续画 7 条，图层命名 `Stroke 1`…`Stroke 8`；工具栏没有颜色、粗细、硬度或笔刷预览控件。
- 画布显示宽度约 858px，内部 1920px；4px 内部笔宽在屏幕上约 1.8px，视觉上很细。
- 选择工具只对 AI 生成图层生效；笔迹图层不能被选中、移动或改样式。

**用户影响（假设，无访谈/无行为数据）**

- 用户只能画细黑线，无法做最基础的草图分区、上色或强调；这会把产品限制在“AI 演示画布”，而不是可用的绘画工具。
- AI 能生成彩色 SVG，用户自己的笔却只能是黑色，人机协作的体验不对称。
- 用户可能因为“笔太细”而反复描线，增加图层数量，进一步挤压图层面板和 AI 对话区。

**建议**

本轮不做完整笔刷引擎，只补两个最小控制：

1. **颜色**：工具栏放一排常用色板（黑、深灰、红、橙、蓝、绿）+ 自定义颜色输入；不要放白色（白底上不可见，容易让用户以为坏了）。
2. **粗细**：2 / 4 / 8 / 16 四档，配一个圆点或线宽预览；默认可从 4 调到 6 或 8，让 44.8% 显示下仍然可见。
3. 设置保存在 `tool-store` 的会话状态即可，本轮不要求跨刷新持久化；刷新回默认值需要在交互上可接受。
4. 不新增图层类型、不改变 `LayerContent`、不做硬度/压感/纹理；这些属于后续笔刷引擎。

**验收标准**

- Given 用户选择红色、宽度 8，when 画一条线，then 新图层的 Fabric path 使用红色和对应宽度，已有图层不变。
- Given 用户切换颜色/粗细，when 继续画，then 新笔画使用新设置，不需要刷新。
- Given 刷新页面，then 颜色/粗细回到默认值（本轮可接受），但画布和图层内容不变。
- Given 键盘用户，then 色板和粗细按钮可 Tab 聚焦、有 `aria-label`，不依赖颜色单独传达状态。
- Given 1920×1080 画布在 1264×625 视口显示，then 默认笔宽在屏幕上至少约 3px，避免“看不见的笔”。

**备注**

这是“现有能力优化”里价值最高的一项，但它是增强而非止血。若本轮只能做 5 件事，它排第 6；不建议拖到下一个大版本。

### F-09 没有真实保存状态；保存失败时笔画可能被移除，只剩 12px 红字

**严重度:** P1（条件性 P0） · **工作量:** M · **置信度:** 80% · **类型:** 保存反馈 / 条件性数据丢失

**现场证据**

- 画布页没有「保存中 / 已保存 / 保存失败」常驻状态；`saving` 只用于禁用撤销、重做、删除。
- 保存失败时，`error` 显示在菜单栏 `menu-status`，样式是 12px 红字，容易被忽略。
- `CanvasStage.tsx` 的 `handlePathCreated` 在 `createLayer` 失败时执行：
  ```ts
  .catch(() => {
    pendingJsonRef.current.delete(json);
    canvas.remove(path);
    canvas.requestRenderAll();
  });
  ```
  即：保存失败时，刚画的笔画会从画布上被移除；用户只看到菜单栏一行小字。
- 服务端在每次 mutation 后持久化，刷新恢复已验证；但客户端没有把“已保存”告诉用户。
- 自动下载是当前唯一的“保存可见行为”，但它是错误的（见 F-03）。

**用户影响（假设，无访谈/无行为数据）**

- 正常网络下用户不知道笔画是否已保存，可能提前刷新或关闭页面。
- daemon 重启、SQLite 写失败、网络代理抖动时，笔画会消失；用户可能连续画多笔后才发现，损失更大。
- 12px 红字不足以让用户意识到“这笔没保存”；没有重试按钮，用户只能重画。

**建议**

1. 状态栏增加保存状态：`保存中…` → `已保存 14:32` → `保存失败 · 重试`；用 `aria-live="polite"`，不要只靠颜色。
2. 保存失败时**不要立即移除笔画**。把 path 留在画布上，标记为“未保存/待重试”；提供重试按钮。只有用户主动放弃或明确失败多次后，才回滚。
3. 保存失败的错误信息要可操作：说明“本地服务未连接/保存失败”，提供「重试」和「导出备份」；不要只显示后端原文。
4. 记录最后一次成功保存的 revision；避免把“撤销/重做成功”误显示成“已保存”。
5. SSE 连接状态（已连接/已断开）归 `07-cross-cutting`，本文件只承诺保存状态；但两者可以在同一个状态栏区域呈现。

**验收标准**

- Given 用户画一笔，when 请求发出，then 状态栏先显示「保存中…」，服务端成功后显示「已保存」，并带最近保存时间。
- Given 模拟保存失败（停 daemon 或返回 500），when 用户画一笔，then 笔画仍留在画布上，状态栏显示「保存失败 · 重试」，不静默消失。
- Given 用户点击「重试」，when 服务恢复，then 未保存笔画成功写入，状态变为「已保存」。
- Given 保存失败，when 用户刷新页面，then 至少有明确警告“有未保存内容可能丢失”，而不是无提示刷新。
- Given 屏幕阅读器，then 保存状态变化会被播报，但不会每 100ms 重复朗读。

**备注**

“保存失败移除笔画”是源码推断，现场未复现。请工程按验收标准在停 daemon 的情况下复现一次；如果确认，严重度升级为 P0。

**现场证据**

- 菜单栏：`Untitled`
- 画布下方：`Untitled · 1920 × 1080`
- 状态栏：`1920 × 1080`
- 状态栏：`缩放: 100%`（不真实）
- 状态栏：`画笔`

- 画布下方 hint 占用垂直空间，在 625px 高的视口里进一步压缩画布和侧栏。

4. 可选：显示当前选中的图层名，但不要与图层面板重复过多；本轮可不做。

**验收标准**

- Given 有画布，then 画布名称只在一个可编辑位置出现，尺寸只在一个位置出现。
- Given 有画布，then 状态栏包含真实缩放和保存状态，不包含硬编码的 100%。
- Given 1264×625 视口，then 移除重复 hint 后画布/侧栏没有新的溢出或遮挡。
- Given 无画布，then hint 只用于空状态文案，不显示 `Blank 1920 × 1080 canvas`。

### F-11 导出没有反馈，JSON 被误认为可恢复的工程文件

**严重度:** P2 · **工作量:** S · **置信度:** 85% · **类型:** 反馈 / 预期管理

**现场证据**

- 点击「导出 PNG」「导出 JSON」后没有 toast、没有状态变化；下载由 anchor 触发。
- JSON 内容包含 `version: "1.0"`、`exportedAt`、完整 `canvas`，但没有导入入口。
- 文件名均为 `Untitled.png` / `Untitled.json`；没有导出尺寸/格式选项。
- 导出错误显示在菜单栏 12px 红字；没有重试。

**用户影响（假设，无访谈/无行为数据）**

- 用户不确定导出是否成功，可能重复点击，产生多个 `Untitled (1).png`。
- 用户看到 JSON 里有完整 canvas，会合理地期待“以后可以导入恢复”，但产品没有导入；这会制造错误的安全感。
- 导出文件重名会让用户找不到最新版本。

**建议**

1. 导出后显示轻量 toast：「已发起下载：红色练习.png（1920×1080）」；不要声称“已成功保存到磁盘”，因为浏览器可能拦截。
2. JSON 按钮文案或 tooltip 标注「导出 JSON（备份，暂不支持导入）」；在帮助文案中说明它用于备份/调试，不是工程文件。
3. 文件名使用画布名 + 时间戳（与 F-05 一起），避免重复覆盖。
4. 导出失败时在按钮附近显示可操作错误和重试，不要只写菜单栏红字。
5. 本轮不做导入、格式选项、尺寸选项；这些是后续能力。

**验收标准**

- Given 用户点击「导出 PNG」，then 出现 toast，包含文件名和尺寸；重复点击不会产生无法区分的同名文件。
- Given 用户点击「导出 JSON」，then 按钮/tooltip 明确写「备份，暂不支持导入」。
- Given 下载被浏览器拦截，then 用户看到“下载可能被拦截”的提示，而不是以为什么都没发生。
- Given 导出失败，then 错误可见、可重试，且不会把当前画布状态改坏。

## 5. 已验证可用（不要重做）

这些能力现场验证通过，本轮不要为了“优化”而重写：

- 新建画布 → 画线 → 刷新，图层和笔迹保留。
- AI 生成图层 → 刷新，图层保留。
- `Ctrl+Z`、`Ctrl+Y`、`Ctrl+Shift+Z` 可用；输入框聚焦时不会拦截。
- 隐藏图层后撤销可以恢复可见性；按钮禁用状态随历史变化。
- 多标签同 `canvasId` 同步：第二标签画一笔，第一标签约 1.2 秒内出现新图层。
- 有画布时 PNG/JSON 导出能产生文件；PNG 内部尺寸 1920×1080。
- 服务端逐次 mutation 持久化；刷新恢复 `canvasId`、图层、修订。

**产品判断：** 持久化不是本轮要补的短板；本轮的短板是“让用户看见持久化发生了”。

| 1 | 空画布不再可画 | F-01 | 确定性数据丢失；首次用户先画一笔就会触发 | 无画布时画笔禁用、画布无路径、空状态 CTA 可见 |
| 2 | 停止假保存，建立真状态 | F-03 + F-09 + F-07 | 自动下载污染文件系统；保存失败可能丢笔画；状态栏还在说假话 | 停笔 5 分钟 0 下载；保存失败笔画不消失；状态栏显示真实比例与保存状态 |
| 3 | 新建画布不丢入口 | F-04 | 误点即失去旧画布访问路径；用户感知为数据丢失 | 有确认；一次操作可返回上一张；失败不覆盖旧 id |
| 4 | 首次进入有唯一主 CTA | F-02 | 创建入口埋在右上角；“尚未加载”误导；AI 空承诺 | 画布区主 CTA；AI 禁用并说明原因；错误/空状态可恢复 |
| 5 | 命名唯一、文件可识别 | F-05 + F-06 | 所有导出都叫 `Untitled`；重名导致删错图层 | 默认名唯一；重命名可用；`Stroke 9` 不重名；导出文件名可区分 |

**第 6 项（本轮必做，但不属于止血）：F-08 画笔颜色/粗细。** 它不修不会“坏”，但不做就无法把现有画笔能力优化到可用；建议紧接 Top 5 之后。

**P2 顺带做：** F-10 状态栏去重、F-11 导出反馈。它们可以和 F-05/F-07 合并到同一个状态栏/导出改造里，成本很低。

## 8. 建议实施顺序

### 第 0 波：止血（约 0.5–1 天）

1. **F-01**：无画布时禁用画笔/选择，画布区加空状态遮罩，`handlePathCreated` 加 guard。
2. **F-03**：删除 30 秒自动下载 effect。
3. **F-06**：笔画命名改为最大 `Stroke N` + 1。

这三项都是 S，能立刻消除“确定性丢笔画”“文件污染”“重名误删”。

### 第 1 波：首次体验与状态可信（约 1–2 天）

4. **F-02**：空状态主 CTA、错误状态、AI 禁用、英文文案清理。
5. **F-09**：保存状态 + 保存失败保留笔画 + 重试。
6. **F-07**：真实缩放显示。
7. **F-10**：状态栏去重，把保存/缩放收进同一区域。

F-02 与 F-01 改同一个画布区，建议同一个人连续做；F-09 依赖 store 暴露最后一次保存结果，先定状态机再写 UI。

### 第 2 波：画布身份与恢复（约 2–3 天）

8. **F-04**：新建确认 + 单级返回；先和工程确认用“previousCanvasId”还是“pushState + popstate”。
9. **F-05**：快速缓解（默认名/文件名时间戳）→ 完整重命名（PATCH + inline edit）。
10. **F-11**：导出 toast 与 JSON 预期管理。

F-05 的快速缓解可以先上，不必等 PATCH 端点；完整重命名需要补 spec 的 Canvas API。

### 第 3 波：创作控制（约 2–3 天）

11. **F-08**：颜色色板 + 四档粗细 + 预览；只改 `tool-store` 和画笔初始化，不改数据模型。

**为什么不先做 F-08：** 颜色/粗细是价值增强，不是止血；如果先做它，用户仍然会在空状态丢第一笔、被自动下载打断、找不到旧画布。先把信任修好，再让笔更好用。

## 9. 开放问题 / 假设

| # | 问题 / 假设 | 当前判断 | 如何验证 |
|---|---|---|---|
| 1 | 没有用户访谈、行为数据、支持票据 | 所有用户影响均为假设；优先级基于现场路径与代码风险 | 找 5 位首次用户做任务测试：打开→画第一笔→刷新→导出→新建 |
| 2 | 自动下载是否会在真实 Chrome 中每 30 秒重复 | 代码是 `setInterval`，逻辑上会重复；现场只验证 33 秒第 1 次 | 真实 Chrome 停笔 2 分钟，记录下载次数与浏览器提示 |
| 3 | 首次访问是否应自动创建画布 | 本轮建议显式 CTA，不自动创建 | A/B 或 5 人任务测试：显式 CTA vs 自动创建的首笔完成率 |
| 4 | 无画布时 AI 应该禁用还是“发送即建画布” | 先禁用，避免空承诺；发送即建是后续优化 | 观察用户是否在空状态先找 AI；若比例高，再考虑发送时创建 |
| 5 | 画布重命名需要新增 `PATCH /paint/canvas/:id` | 需要补 spec 一行；不改数据模型 | 工程评估 S/M；若成本高，先做默认名 + 文件名时间戳 |
| 6 | “100%”到底指内部像素还是显示比例 | 用户看到的是 44.8%，应显示“适应窗口 45%” | 与设计/工程确认状态栏语义；不要继续硬编码 |
| 7 | 保存失败时笔画被移除是否会在真实环境发生 | 源码推断；若复现则升级 P0 | 停 daemon 后画一笔，观察画布、网络请求、菜单错误 |
| 8 | 单级返回用 localStorage 还是浏览器 history | 两者都可；优先选改动小、不会污染 history 的方案 | 工程评估 F-04 方案 A/B；确认 `popstate` 能加载 `canvasId` |
| 9 | 画笔颜色/粗细是否需要跨刷新持久化 | 本轮会话级即可，不扩大存储范围 | 用户测试：刷新后回默认是否造成明显困扰 |
| 10 | AI 生成图层是否也会重名 | 现场未观察；先修 `Stroke` 命名，不承诺 AI 命名 | 连续让 AI 生成同名图层，检查列表与删除确认 |

## 10. 后续建议（不进本轮待办）

这些不是本轮范围，只作为后续触发点记录：

- **画布列表/画廊**：当单级返回仍无法满足“我有多个作品”时，再做最近画布列表；需要 `GET /paint/canvas` 列表端点与缩略图策略。
- **模板/示例画布**：当首次用户仍不知道画什么时，提供 2–3 个可一键开始的示例；不要先做完整教程。
- **JSON 导入 / `.aipaint`**：当用户明确需要跨设备恢复或工程文件时，再设计文件格式；本轮只把 JSON 标注为备份。
- **完整缩放/平移**：当用户反馈“看不清细节/笔太粗”时，再做 viewport 控件；先把真实比例显示修对。
- **笔刷引擎**：当颜色/粗细仍不够时，再考虑硬度、压感、纹理；不要在本轮把简单画笔扩成复杂工具。

## 11. 一句话结论

PaintCodex 的 Phase 1 已经能“画、存、刷新、导出”，但首次体验被三个假象拖累：**假画布、假 100%、假保存**。本轮不需要新模块，只需要把这三个信号改成真的，再补上画布身份和画笔颜色/粗细，产品就会从“能演示”变成“敢让用户用”。
