# 图层与选择体验审计

**审计人**: Alex（产品经理）  **日期**: 2026-10-26  **版本**: v1
**输入**: `.scratch/product-audit/evidence/`（真实 Chrome 现场采集，1264×625，DPR 1）、`.scratch/phase-1-mvp/spec.md`、`docs/adr/0003`、`GLOSSARY.md`、`apps/web` 与 `packages/protocol` 源码
**限制**: 本子智能体无浏览器执行权限，未做用户访谈与行为数据分析。所有"用户影响"在无访谈支撑处标注「假设」，并给出置信度。

---

## 1. 审计范围

**在范围内**：图层面板的列表结构、行交互、可见性与删除、名称/类型/透明度的信息暴露、目标尺寸与键盘可达性、图层数量增长时的面板布局、图层选择与画布反馈的一致性、多标签同步时的图层可见性。

**不在范围内**：AI 对话交互（见 `04`）、画笔参数（见 `02`）、导出与持久化（见 `05`）、监控（见 `06`）、响应式与全局本地化（见 `07`）。引用处标注交叉索引，不在此重复定级。

**本轮原则**：不新增板块。协议里已有、数据模型已有、但 UI 没有暴露的能力算"完善现有能力"；需要改协议、改数据模型、或 spec 明确列为后续的，一律标为后续。

## 2. 体验路径摘要（依据现场证据）

1. 新建画布 → 画笔连续画 8 条，图层列表出现 `Stroke 1` … `Stroke 8`，类型列显示英文 `vector`。
2. 切到「选择」工具，点图层行：只有行边框/背景变化（`layer-item--active`），画布无任何轮廓或选中框；笔迹图层在画布上不可点击（`selectable/evented=false`）。
3. 点可见性按钮（实测 7×11 px）：画布非白像素 13165 → 9203，隐藏生效；按钮 `aria-label` 从「隐藏 Stroke 1」变为「显示 Stroke 1」，`aria-pressed=false`。
4. 删除中间的 `Stroke 4`：弹出原生 `window.confirm('删除图层 "Stroke 4"?')`；确认后无 toast、无"撤销"入口，只能去工具栏撤销。
5. 再画一条：新图层仍叫 `Stroke 8`，列表出现两条同名项：`["…","Stroke 8","Stroke 8"]`。
6. 图层到 8 层时，侧栏 `scrollHeight 595 > clientHeight 556.75`，AI 对话从单层时的约 467px 被压到 186.75px，聊天区底部 600.75 已逼近状态栏上沿（工作区底部约 597）。
7. 打开第二个标签页：图层与可见性一致；在 B 页画一条，A 页 1.2 秒内 8 → 9 层。但画布页没有任何"已连接 / 已断开"指示。

## 3. 严重度定义

| 级别 | 定义 | 处理要求 |
|---|---|---|
| **P0** | 核心任务无法完成，或已造成/极易造成不可恢复的数据损失与信任破坏 | 本轮必须修，阻塞发布 |
| **P1** | 任务可完成但存在明显摩擦、误导或高风险误操作；违反基本可用性/无障碍底线 | 本轮必修，进入本轮迭代 |
| **P2** | 打磨项，不影响任务完成，但影响专业感与效率 | 本轮尽量修，允许延后一轮 |

判级参考：触达面（多少用户/多高频）× 可恢复性（出错后能否挽回）× 是否有替代路径。

### L-01 图层行不可键盘选中

**严重度**：P1　**工作量**：S　**置信度**：高

**现场证据**
- `evidence/03-layers.md`：可访问性树为 `listitem "● Stroke 1 vector ×" [clickable, cursor:pointer]`；`tabIndex = -1`、无 `role`、无键盘事件；Tab 只能到达两个内部按钮。
- 源码 `apps/web/src/features/layer-panel/LayerPanel.tsx`：`<li onClick={() => setActiveLayer(layer.id)}>`，无 `tabIndex`、无 `onKeyDown`。
- `evidence/07-cross-cutting.md`：无全局 `:focus-visible` 样式，依赖浏览器默认轮廓。

**用户影响**（假设）：纯键盘用户、读屏用户完全无法执行"切换当前图层"这一动作；而视觉用户点一下就行，形成能力分层。该动作目前本身没有功能后果（见 L-03），所以实际损害被 L-03 掩盖——两者必须一起修，否则"修好键盘可达"也只是让人更方便地做一件没有效果的事。

**建议**
- 列表改用 `role="listbox"` + 行 `role="option"` + `aria-selected`，行 `tabIndex=0`；或（更小改动）行 `tabIndex=0` + `role="button"`，Enter/Space 触发与点击相同行为。方向键上/下在行间移动焦点，`Delete` 触发删除（需确认）。
- 必须同时提供可见的 `:focus-visible` 轮廓（≥2px，与背景对比 ≥3:1），深色背景上不能只依赖默认描边。
- 行内已有两个按钮，键盘路径要明确：Tab 进入行 → Tab 进入可见性 → Tab 进入删除，不能出现"进得去出不来"。

**验收标准**
- [ ] Given 键盘用户在页面内，when 按 Tab 至图层列表，then 焦点落在第一行且轮廓清晰可见。
- [ ] Given 焦点在某一行，when 按 ↑/↓，then 焦点移动到相邻行，且 active 状态与该行一致。
- [ ] Given 焦点在某一行，when 按 Enter 或 Space，then 行为与鼠标点击完全一致，且 Space 不导致页面滚动。
- [ ] Given 焦点在某一行，when 按 Tab，then 依次到达该行可见性按钮与删除按钮，再按 Tab 进入下一行或离开列表。
- [ ] Given 读屏开启，when 聚焦某行，then 播报"图层名 + 类型 + 是否可见 + 是否为当前图层"。

### L-02 可见性 7×11、删除 16×16，远低于最小点击目标

**严重度**：P1　**工作量**：S　**置信度**：高

**现场证据**
- `evidence/03-layers.md` 实测（1264×625）：`{"name":"隐藏 Stroke 1","w":7,"h":11}`、`{"name":"删除 Stroke 1","w":16,"h":16}`；对照工具按钮约 39×36、菜单按钮高 32。
- `apps/web/src/features/layer-panel/layer-panel.css`：`.layer-item__visibility { padding:0; font-size:11px }`、`.layer-item__delete { padding:0 2px; font-size:16px }`。

**判断**：不是 P0。现场鼠标点击可见性**成功**（像素 13165 → 9203），说明桌面鼠标下可用；但 7×11 已低到"必须瞄准"，删除 16×16 紧邻其右侧，且删除是破坏性操作、无就地撤销（L-06）。对触控板误触、手抖、触屏、低视力用户，这是典型的"高风险 + 低容错"组合。WCAG 2.5.8 AA 最低目标 24×24；常见触控建议 44×44。因此定 P1：**本轮必修，但不阻塞发布**。

**取舍（重要）**：把行高从约 33–34px 抬到 40px 会让 8 层从约 314px 涨到约 362px，与 L-07 直接冲突（当前 8 层已把聊天压到 186.75px）。所以 L-02 必须在 L-07 的"图层区上限 + 内部滚动"之后或同批实施，不能单独放大按钮然后不管布局。

**建议**
- 可见性按钮点击区 ≥ 24×24（目标 28×28），删除 ≥ 24×24，两按钮之间水平间距 ≥ 8px；行高控制在 ≤ 40px。
- 删除按钮的 hover 态已有红色（`#e07a7a`），补 `focus-visible` 与 `active` 态；破坏性操作的视觉权重不要高于可见性。
- 若行高维持在 36px 以内，用"热区扩展"（`padding` + 负 margin 或伪元素）而非放大字形，避免视觉噪音。

**验收标准**
- [ ] Given 1264×625 视口、DPR 1，when 读取 bounding box，then 可见性 ≥ 24×24、删除 ≥ 24×24、两者间距 ≥ 8px。
- [ ] Given DPR 2 与浏览器缩放 125%，when 重复测量，then 上述尺寸仍成立（用 CSS px 校验）。
- [ ] Given 光标落在按钮外 4px 内但仍在热区内，when 点击，then 触发对应动作（验证热区而非视觉尺寸）。
- [ ] Given 8 个图层，when 测量图层面板高度，then ≤ 300px（与 L-07 验收联动）。

### L-03 「当前图层」是空转状态：点击只换边框，画布无反馈

**严重度**：P1　**工作量**：M　**置信度**：高

**现场证据**
- `evidence/03-layers.md`：当前图层"只通过边框/背景色区分"，"画布上不会出现对应轮廓（笔迹图层不可选中）"；点击笔迹图层"只改变 active 状态，画布上没有反馈"。
- `evidence/04-ai-chat.md`：AI 生成图层仅在「选择」工具下可移动/缩放，变换后写回 SVG。
- 源码事实：`activeLayerId` 只被 `LayerPanel.tsx` 用于拼 class 名，其余出现位置全在 `canvas-store.ts` 的默认值与合并逻辑；`CanvasStage.tsx` 完全不读 `activeLayerId`。画笔每一笔都新建图层，所以"当前图层"从来不是绘制目标。
- `LayerPanel.tsx` 的 `<li>` 有 `cursor:pointer` + `onClick`，等于向用户承诺"这里可以选中/操作图层"。

**用户影响**（假设）：用户点击行 → 看到蓝色边框 → 期待画布高亮或后续操作作用于该图层 → 实际什么都没发生。这是"诱饵交互"，比没有交互更伤信任；也会让人误以为笔迹图层坏掉了（L-08）。这一条比"缺重命名"更能解释现场那种"点了没反应"的挫败。

**建议**
- 定义 `activeLayerId` 的唯一含义（见开放问题 Q1）。在含义确定前，本轮先做最小闭环：
  - AI 生成图层：点击行 → 若当前工具是「选择」，把对应 Fabric 对象设为 `activeObject`，画布出现变换框；若当前工具是「画笔」，保持工具不变，但画布对该对象显示 1.5s 选中框（或直接切到选择工具——二选一，需产品定，见 Q1）。
  - 笔迹图层：点击行 → 画布对该路径做短时高亮（描边/阴影，≤800ms）。**技术可行性需交回父 agent 验证**（Fabric path 临时改 `strokeWidth`/`shadow` 再还原，或叠加一层高亮副本）；若成本 > S，则退化为 L-08 的文案方案。
  - 面板内在行首加"当前"标识（或标题区显示"当前：Stroke 3"），让状态不只靠一行 1px 边框颜色。
- 若决定不赋予任何行为，则必须去掉 `cursor:pointer` 与整行点击，只保留两个按钮——这是可接受的"诚实降级"，但要与 L-01 的键盘方案一起重做，不能留半套。

**验收标准**
- [ ] Given 画布有 1 个 AI 生成图层与 3 个笔迹图层，when 点击 AI 行，then 画布出现该对象的变换框（`activeObject` 唯一），并可在画布上拖动，`object:modified` 后内容写回。
- [ ] Given 同上，when 点击任一笔迹行，then 画布在 800ms 内出现该路径的高亮，且 800ms 后完全恢复原样（像素差为 0）。
- [ ] Given 点击某行后刷新页面，then 不因 active 状态产生任何数据变化（active 不是持久化状态）。
- [ ] Given 点击另一行，then 前一行的高亮/变换框消失，任意时刻最多一行 active。

### L-04 名称、透明度、类型标签未暴露已有数据能力

**严重度**：P1　**工作量**：M　**置信度**：高

**现场证据**
- `evidence/03-layers.md`：名称、类型、可见性都是文本，"没有可编辑输入"；"没有 opacity/rename/reorder 控件"。
- `packages/protocol/src/index.ts`：`Layer` 有 `name`、`opacity`、`zIndex`；`UpdateLayerPatch` 支持 `name`、`visible`、`opacity`、`content`。
- `apps/daemon/src/paint/service.ts`：`canvas_update_layer` 直接调用 `layers.update(canvasId, layerId, patch)`，无字段白名单限制。
- `apps/web/src/features/canvas/CanvasStage.tsx`：同步时已执行 `existing.set({ visible: layer.visible, opacity: layer.opacity })`——**渲染端已支持透明度**，UI 缺的只是入口。
- `LayerPanel.tsx`：类型标签直接渲染 `layer.type`，即英文 `vector`。

**判断**：`name` 与 `opacity` 属于典型的"协议和渲染都好了，只差一个控件"，符合"完善现有能力"的定义，本轮应做。`zIndex` 虽然存在于模型，但 `UpdateLayerPatch` 没有这个字段，且 `spec.md` 明确把 "Layer reordering/merging" 列为 Phase 2+——**排序不是本轮能力完善，是协议扩展**，见第 6 节。

**落地注意（快照撤销的副作用）**：ADR-0003 是快照级撤销，每个 mutation 写一个快照、只保留 20 个。透明度滑块若在 `input` 事件里连续 PATCH，一次拖动会吃掉十几个撤销步，并让 AI 对话/绘制的撤销历史被冲掉。必须：**拖动过程只改本地预览，`change`（松手）才发一次 PATCH；一次拖动 = 一个撤销步**。名称同理：Enter/失焦提交一次。

**建议**
- 行内重命名：双击名称或行内小按钮进入 `input`；Enter 提交、Esc 取消、失焦提交；空值回退原名；长度上限 60 字符，超长省略显示（title 给出全名）。
- 透明度：行内滑块 + 百分比数字（0–100%，步进 5%），或折叠在行尾的"属性"小浮层；**不要**为它新开一个属性面板板块。
- 类型标签本地化：`vector` → 「笔迹」，`ai-generated` → 「AI」，`raster` → 「图片」；颜色仍是 11px 次要文本，但需满足对比度（见 L-10）。
- 名称变更必须同步到：删除确认文案、`aria-label`、导出 JSON 的 `layer.name`、以及后续 AI 上下文（Context Builder 读的是 `name`，改名会影响提示词内容——需在 ticket 中标注）。

**验收标准**
- [ ] Given 某图层 `Stroke 3`，when 双击名称改为「天空」并回车，then 列表立即显示「天空」，刷新后仍为「天空」，导出的 JSON 中该层 `name` 为「天空」。
- [ ] Given 编辑中，when 按 Esc，then 名称恢复为「Stroke 3」，不产生 PATCH。
- [ ] Given 名称清空后提交，then 回退原名并给出一次行内提示，不发送空名称请求。
- [ ] Given 某图层，when 把透明度拖到 40% 并松开，then 画布该层不透明度为 0.4，刷新后保持，且**撤销一次即回到拖动前的值**（不是 40 次）。
- [ ] Given 任意图层，then 类型列不再出现英文 `vector`（笔迹显示「笔迹」）。
- [ ] Given 重命名包含 `<`、`"`、制表符，then 显示与 `aria-label` 不出现 HTML 注入或布局破坏。

### L-05 默认命名会重名

**严重度**：P1　**工作量**：S　**置信度**：高

**现场证据**
- `evidence/02-canvas-brush.md`：画到 `Stroke 8` → 删除 `Stroke 4` → 再画一条，结果 `["Stroke 1",…,"Stroke 8","Stroke 8"]`。
- `apps/web/src/features/canvas/CanvasStage.tsx`：`name: \`Stroke ${current.layers.length + 1}\``。

**用户影响**（假设，置信度中）：重名本身不破坏数据（`id` 唯一），但破坏**可识别性**：删除确认弹窗写「删除图层 "Stroke 8"?」，读屏名称重复，用户无法判断要删哪一条。与 L-02（16×16 删除按钮）叠加，是明确的误删路径。这属于 P1，不是纯美化。

**建议**
- 用 `max(现有 Stroke 编号) + 1`，或维护画布级递增计数器；若历史已存在重名，只保证**新**图层不重名，不自动改名旧图层（自动改名会静默改动用户数据，违反"惊喜就是失败"）。
- 与 L-04 的本地化一起决策：默认名是否改为「笔迹 1」（见 Q3）。若改，需考虑已有 `Stroke N` 数据的兼容显示。

**验收标准**
- [ ] Given 8 个图层，when 删除 `Stroke 4` 后再画一条，then 新图层名为 `Stroke 9`（或「笔迹 9」），全列表无重名。
- [ ] Given 已存在 `Stroke 1`、`Stroke 3`，when 新建图层，then 名称为 `Stroke 4`。
- [ ] Given 列表中任意两项，then `name` 字符串互不相同（可用于删除确认与读屏区分）。

### L-06 删除依赖原生 confirm，删除后无就地反馈与撤销入口

**严重度**：P1　**工作量**：M　**置信度**：中高

**现场证据**
- `evidence/03-layers.md`：`window.confirm('删除图层 "xxx"?')`；现场浏览器默认自动取消（headless 行为），无自定义弹层；删除后无 toast、无"已删除，撤销"；只能依赖工具栏撤销。
- `LayerPanel.tsx`：`handleDelete` 直接用 `window.confirm`；删除按钮 `disabled={saving}`。
- `apps/daemon/src/paint/service.ts`：每次动作（含 `canvas_delete_layer`）在 bump revision 后 `recordSnapshot`，撤销走 `snapshots.before(cursor)`。**因此删除是可撤销的**（机制同现场已验证的"隐藏后撤销恢复可见性"），但**"删除后撤销"本身未在现场验证**，置信度因此定为中高，需父 agent 补验。
- 已知约束：`SNAPSHOT_LIMIT = 20`，删除后 20 次操作即无法回退。

**用户影响**（假设）：原生 confirm 是浏览器级模态，样式与应用完全脱节，且会阻塞渲染与 SSE 回调；更关键的是**删除成功后没有任何确认信号**——列表少一行，用户不确定是删掉了还是被同步刷新覆盖了。配合 L-05 重名，用户可能删错且不自知。反过来，如果直接去掉 confirm 而不给撤销入口，破坏性操作就裸奔了。所以"确认"与"可恢复"必须一起设计，不能只删弹窗。

**建议（最小闭环，不引入全局 toast 体系）**
- 去掉 `window.confirm`，改为**删除即执行 + 图层面板内就地出现一条 5–8 秒的恢复条**：`已删除「Stroke 4」 · 撤销`。点击撤销调用现有 `undo()`（一次快照回退），不新增接口。
- 恢复条放在图层面板顶部（`role="status" aria-live="polite"`），不遮挡图层行；同一时间只保留最近一条（新的覆盖旧的）。
- 失败路径：删除失败时就地显示 `删除失败：<原因> · 重试`（`role="alert"`），不要只写进菜单栏 12px 红字（见 L-13）。
- 若担心"直接删除太激进"，可用**行内二段确认**（第一次点击把该行删除按钮变为「确认删除？」，2.5s 后回退），成本与恢复条相当，但少一次网络往返；二选一即可，**不要两者都做**。

**验收标准**
- [ ] Given 3 个图层，when 点击某行删除，then 不再出现浏览器原生 confirm，图层在 1 个网络往返内消失。
- [ ] Given 刚删除一层，then 图层面板顶部出现恢复条，文案含被删图层名，8 秒后自动消失。
- [ ] Given 恢复条可见，when 点击「撤销」，then 图层恢复（名称、可见性、zIndex、内容一致），画布像素数与删除前一致（±0）。
- [ ] Given 连续删除两层，then 只显示最近一条恢复条；点撤销恢复最近删除的一层。
- [ ] Given 删除请求失败（daemon 关闭），then 行保留、就地显示可重试的错误，不出现"看起来删掉了但刷新后又回来"的错觉。
- [ ] Given 恢复条消失后，then 工具栏撤销仍可恢复该图层（受 20 快照上限约束，文案不承诺"永久可恢复"）。

### L-07 图层增长挤压 AI 对话，侧栏整体滚动

**严重度**：P1　**工作量**：S　**置信度**：高

**现场证据**
- `evidence/03-layers.md`（8 层）：`layerPanel {h:370, scrollH:369}`、`sidePanel {h:556.75, scrollH:595}`、`chat {y:414, h:186.75, bottom:600.75}`、视口 625，工作区底部约 597。
- 单层时图层面板约 90px、AI 对话约 467px（`evidence/04-ai-chat.md` 同结论）。
- `apps/web/src/app/app.css`：`.side-panel { display:flex; flex-direction:column; overflow-y:auto }`，图层面板与 AI 面板没有高度分配规则。
- `apps/web/src/features/ai-chat/ai-chat.css`：`.ai-chat__messages { max-height: 280px }`，不参与收缩。

**用户影响**（假设，置信度中高）：图层越多（越是认真在用这个产品的人），AI 对话越小；输入框被推到状态栏边缘甚至折叠线以下，用户要滚动整个侧栏才能提问。这是"用得越深、体验越差"的反向曲线，和本轮"把现有能力优化到极致"的目标直接冲突。8 层是很容易达到的数量（现场画 7 条 + 1 个 AI 图层）。

**最小修复判断（独立滚动 vs 折叠 vs 分隔条）**

| 方案 | 改动面 | 是否解决"输入框可见" | 风险 | 结论 |
|---|---|---|---|---|
| A. 图层列表独立滚动 + 高度上限 | 纯 CSS + 容器 | ✅ | 新图层可能在滚动区外 | **推荐，本轮做** |
| B. 图层面板可折叠 | 新控件 + 状态 + 记忆 | ✅ | 折叠后看不见图层，需额外入口 | 后续（与 A 不冲突） |
| C. 可拖拽分隔条 | 新控件 + `role="separator"` + 键盘 + 持久化 | ✅ | 最大改动，a11y 成本高 | 后续 |

选 A 的理由：不改信息架构、不加新控件、不动持久化，能在一屏内让"图层多"与"能聊天"同时成立；B/C 都应建立在 A 之上（先有独立滚动，再谈用户手动分配）。

**建议**
- `.side-panel` 不再整体滚动（`overflow: hidden`），改为：图层面板 `flex: 0 0 auto` + `max-height: 300px`（含标题），内部 `.layer-list` 独立 `overflow-y: auto`；AI 面板 `flex: 1 1 auto; min-height: 240px`，消息区 `flex: 0 1 auto` 收缩，输入框常驻底部。
- 新图层/新 AI 图层产生时，若其在滚动区外，自动滚到可见（`scrollIntoView({ block: 'nearest' })`），否则用户会以为"图层没生成"。
- 数值验收按 557px 侧栏高度：图层区 ≤ 300px → 聊天区 ≥ 240px，两者之和 ≤ 557，不得出现侧栏整体滚动。

**验收标准**
- [ ] Given 8 个图层、视口 1264×625，then AI 对话区高度 ≥ 240px（当前 186.75），输入框与「发送」按钮无需任何滚动即可完整可见。
- [ ] Given 20 个图层，then `.side-panel` 的 `scrollHeight === clientHeight`（无整体滚动），图层列表内部可滚动。
- [ ] Given 20 个图层、列表已滚到顶部，when 画一条新笔迹，then 新图层行自动进入可视区。
- [ ] Given 侧栏高度 557px、图层区已达上限，when 图层继续增加，then 聊天区高度保持不变（不再被继续压缩）。
- [ ] Given 折叠 AI 对话，then 图层面板仍受 300px 上限约束，不出现新的整体滚动。

### L-08 笔迹图层不可选中：边界合理，但缺"为什么"的解释

**严重度**：P2　**工作量**：S　**置信度**：高

**现场证据**
- `evidence/03-layers.md`：「选择」工具 title 是"选择和移动 AI 图层"；`CanvasStage.tsx` 中 `selectable = selectMode && layer?.type === 'ai-generated'`。
- `spec.md` 的目标里没有"选中/移动笔迹"；Phase 1 明确不做完整工具集。`GLOSSARY.md` 也只写 AI 生成图层可被选择、移动、缩放。

**判断**：**笔迹不可选中是 Phase 1 的合理边界，不是缺陷**。让笔迹可选中/变换意味着：Fabric 对象 `evented/selectable` 打开、变换后写回 `content.kind='fabric'` 的新 JSON、以及"一笔一图层"与变换的语义冲突——这是新能力，不是完善现有能力。但用户预期落差是真实存在的：点击图层行毫无反馈（L-03）会让"不可选中"从"限制"变成"坏了"。

**建议**
- 不做笔迹变换。做解释与替代路径：类型列显示「笔迹」（L-04），行内 `title`/tooltip 说明「笔迹图层暂不支持在画布上选中，可在右侧隐藏或删除」；「选择」工具的按钮文案/tooltip 保持一致（当前 title 已准确，但 title 不可见）。
- 若 L-03 采用"点击笔迹行 → 画布短时高亮"，本条的预期落差基本消失；否则至少给一次性的引导文案。

**验收标准**
- [ ] Given 笔迹图层，when 悬停类型标签或行，then 出现说明"笔迹图层暂不支持在画布上选中"。
- [ ] Given 「选择」工具激活，then 按钮 tooltip/说明明确只有 AI 生成图层可被选中。
- [ ] Given 用户尝试在画布上点击笔迹路径，then 不发生选择，但也不出现任何"看似被选中又消失"的闪烁。

### L-09 可见性按钮语义混用

**严重度**：P2　**工作量**：S　**置信度**：高

**现场证据**
- `evidence/03-layers.md`：`aria-label` 是动作（「隐藏/显示」），`aria-pressed` 是状态，读屏结果为「显示 Stroke 1，切换按钮，未按下」。
- `LayerPanel.tsx`：`aria-label={layer.visible ? \`隐藏 ${layer.name}\` : \`显示 ${layer.name}\`}` + `aria-pressed={layer.visible}`。

**建议**：标签固定为「{name} 可见性」，`aria-pressed` 表示当前是否可见（或干脆用 `aria-label` 只描述状态）。视觉上图标 `●/○` 语义偏弱，可换成眼睛/眼睛-斜线（若引入图标集则本轮只换这两个，不铺开）。

**验收标准**
- [ ] Given 图层可见，when 读屏聚焦按钮，then 播报包含图层名与"已按下/可见"，且不出现"显示…未按下"这类自相矛盾的组合。
- [ ] Given 点击切换，then `aria-pressed` 与画布可见性、数据库 `visible` 三者一致。

### L-11 图层列表顺序与主流工具相反

**严重度**：P2　**工作量**：S　**置信度**：中

**现场证据**
- `apps/daemon/src/paint/repository.ts`：`ORDER BY zIndex ASC, createdAt ASC` → 列表先底层后顶层；现场 8 层显示顺序为 `Stroke 1 … Stroke 8`，最新绘制的最靠下。

**验收标准**（若实施）
- [ ] Given 3 个图层，then 列表首项为顶层，且与画布遮挡关系一致。
- [ ] Given 新增图层，then 新行出现在列表首项并自动可见。

### L-12 多标签同步有效但无连接状态

**严重度**：P2　**工作量**：M　**置信度**：中

**现场证据**
- `evidence/03-layers.md`：第二标签页图层与可见性一致；B 页画一条，A 页 1.2 秒内 8→9 层。
- 画布页无连接指示；`apps/web/src/runtime/paint-sse.ts` 提供 `onError`，`App.tsx` 未传入；`onOpen` 仅用于刷新。

**用户影响**（假设）：同步正常时用户无感（这是对的）；但 daemon 关闭/网络中断时，用户继续画，其他标签页不再更新，界面无提示——用户会归因为"图层丢了"或"画布坏了"，而正确认知应是"离线，待恢复"。

**建议**：最小实现——状态栏加一个连接指示（「实时同步」/「连接中断，正在重连」），断线时不做阻断；重连成功（`onOpen`）已会 `refreshCanvas()`，无需额外逻辑。若 `07` 的"保存/连接状态"票据统一处理，本文件只作为图层侧需求登记，避免两处重复实现。

**验收标准**
- [ ] Given 两个标签页，when 在 B 页新增图层，then A 页 2 秒内出现该图层且无整页刷新闪烁。
- [ ] Given 停止 daemon，then 5 秒内在状态栏可见"连接中断"提示，画布仍可本地绘制。
- [ ] Given daemon 恢复，then 提示消失，且画布与最新 revision 一致（不丢本地已保存内容）。

### L-13 图层操作无 pending/失败就地反馈

**严重度**：P2　**工作量**：S　**置信度**：中

**现场证据**
- `LayerPanel.tsx`：删除按钮 `disabled={saving}`，但可见性按钮与行点击**不**禁用、无 pending 态。
- `canvas-store.ts`：`saving` 是全局布尔，`error` 只写进 store；`App.tsx` 把错误渲染为菜单栏 12px 红字（`evidence/07-cross-cutting.md`）。
- `evidence/03-layers.md`：删除失败无就地提示。

**用户影响**（假设）：可见性点击后约一个往返才生效，用户可能连点两次（结果回到原状）；失败时错误出现在视野之外的菜单栏，用户只看到"点了没反应"。

**建议**：每个图层行维护独立 pending 集（或按钮 `aria-busy` + 降透明度）；图层操作错误在图层面板顶部就地显示（`role="alert"`）并给重试；成功不提示（避免噪音）。

**验收标准**
- [ ] Given 点击可见性，then 200ms 内按钮进入 pending 态，请求完成后恢复，期间重复点击不产生第二次请求。
- [ ] Given 可见性请求失败，then 行内/面板顶部显示错误与「重试」，图标回到与服务端一致的状态。

## 5. Top 5 必须修

按"影响面 × 不可恢复性 × 与其他修复的耦合度"排序：

1. **L-07 面板布局**（P1，S）：8 层就把 AI 对话压到 186.75px，直接打击核心使用路径；且它是 L-02 放大目标尺寸的前置条件。
2. **L-06 删除可恢复性**（P1，M）：破坏性操作 + 只有原生 confirm + 删除后无信号；同时消除 L-05 误删的后果。
3. **L-02 目标尺寸**（P1，S）：7×11 / 16×16 是全产品最低的点击目标，改动小、收益直接，与 L-06 同批做效果最好。
4. **L-04 名称与透明度**（P1，M）：协议、API、渲染全就绪，纯 UI 缺口；"优化到极致"最典型的着力点，但必须遵守"一次拖动 = 一个撤销步"。
5. **L-05 默认命名重名**（P1，S）：与删除确认、读屏名称直接相关，成本极低，不修就会持续制造歧义。

紧邻其后、同批完成的：**L-03（active 空转）** 与 **L-01（键盘可达）**。L-03 决定 L-01 修的到底是不是一个有意义的行为，两者应在同一迭代内闭环，但不单独占用 Top 5 名额。

## 7. 建议实施顺序

**批次 1（布局打底，1 个 PR）**
L-07 面板高度分配 + 图层列表独立滚动 + 新行自动可见。
理由：后续所有"行变高、加控件"的改动都依赖它，否则会把聊天区继续往下压。

**批次 2（图层行的可用性，1 个 PR；依赖批次 1）**
L-02 目标尺寸 → L-05 命名唯一 → L-09 可见性语义 → L-13 pending/错误就地反馈。
理由：都在同一组件同一区域，一次改完，避免三次回归同一片 CSS。

**批次 3（能力补齐，1 个 PR）**
L-04 重命名 + 透明度 + 类型中文化（含 L-10 的对比度取值）。
理由：涉及 PATCH 调用与快照粒度，需要单独测试"一次拖动一个撤销步"。

**批次 4（状态与反馈闭环，1 个 PR）**
L-03 active 语义 + L-06 删除恢复条 + L-01 键盘可达。
理由：三者共享"行作为可操作单元"的语义；先定 active 含义，再让键盘去触发它。删除恢复条与 `undo()` 复用，需父 agent 先现场验证"删除后撤销"。

**批次 5（可延后，视资源）**
L-08 文案、L-11 顺序标识、L-12 连接状态（可能与 `07` 的票据合并）。

预期收益：批次 1–4 完成后，8 层场景下 AI 对话恢复到 ≥240px，图层行可键盘操作、命名唯一、删除可一键恢复、名称与透明度可编辑——全部是已有能力的完整化，没有新增板块。

## 8. 开放问题与假设

### 假设（无证据处明确标注）

- **A1**：证据包无用户访谈、无行为数据。"用户会因点击行无反馈而困惑""7×11 会导致误点""重名会导致删错"均为基于现场行为与界面语义的**假设**，置信度中，需在下一轮用 5 次可用性测试或支持票验证。
- **A2**：假设本轮仍是**桌面优先**（视口 ≥ 1024）。若承诺触屏，L-02 的 24×24 应升到 44×44，行高与 L-07 的上限需重算。
- **A3**：假设图层数量在 Phase 1 内常态为 3–20 层（依据：一笔一图层的实现方式 + 现场 8 层即出现挤压）。若实际会到 50+，L-11、缩略图、搜索的优先级都要上调。
- **A4**：假设"删除后撤销可恢复"成立（依据 `service.ts` 每次动作写快照 + 现场已验证隐藏后撤销）。**未现场验证删除路径**，需父 agent 补测：删除 → 撤销 → 图层 id、名称、zIndex、像素数是否完全恢复。

### 开放问题（需决策，非我能单方面定）

1. **`activeLayerId` 的产品含义是什么？**（a）画布选中对象（AI 生成图层才有意义）；（b）未来绘制的目标图层（需要改画笔逻辑，一图层多笔迹）；（c）仅表示"最近操作/定位"。选 (b) 是产品方向的改变，超出本轮；本轮建议按 (a)+(c) 实现，并在文案上不说"当前图层"而说"选中图层"。
2. **L-03 中点击 AI 行是否应该自动切到「选择」工具？** 好处是"点了就能拖"；坏处是打断正在画的用户。建议：不自动切工具，但显示选中框并在框中提示"切换到选择工具可移动"。
3. **默认命名是否中文化为「笔迹 1」？** 需要与 `GLOSSARY.md` 的术语缺口一起定：目前术语表有 `vector`/`raster` 的英文定义，但没有中文名，UI 直接漏出英文。建议补术语条目后再改名，否则会出现"文档叫 vector、界面叫笔迹"的第三套说法。
4. **删除交互选"直接删 + 恢复条"还是"行内二段确认"？** 我倾向前者（可恢复优于拦截，且与快照撤销一致）；若真实用户对误删更敏感，则后者。需要一次 5 人测试定夺。
5. **同步断开时是否要阻止继续编辑？** 建议不阻止（本地已保存），只提示；但要确认多标签同时编辑时 revision 冲突的重试路径对用户是"自动重试"而非"报错"。
6. **20 个快照的上限对"删除恢复"意味着什么？** 删除后经过 20 次动作就不可恢复。恢复条 8 秒内可用是安全的，但工具栏撤销会被静默消耗。是否需要在图层面板给出"更早的删除不可恢复"的说明？→ 建议不做文案，作为已知限制记入 ticket。

### 需要交回父 agent 验证的技术问题

- 删除后撤销的端到端恢复（见 A4）。
- L-03 中"笔迹路径短时高亮"的可行性与成本：Fabric `Path` 是否有稳定的临时样式改动方式（改 `stroke`/`strokeWidth`/`shadow` 后还原），是否会被 `CanvasStage` 的签名比对/SSE 刷新打断。若成本 > S，本条降级为纯文案方案。
- L-04 透明度滑块在 `change` 提交时的 PATCH 时序：是否与 `saving` 全局锁、`enqueueMutation` 串行队列冲突（连续快速改多层时是否需要 per-layer 队列）。
- L-07 的 `.side-panel { overflow: hidden }` 是否会影响监控页以外的既有布局（`.workspace` 网格的 `min-height: 0` 链路）。
