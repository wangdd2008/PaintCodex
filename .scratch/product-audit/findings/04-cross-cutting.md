## 0. 结论先行

1. **桌面主路径可用，问题集中在「系统状态不可见」。** 保存、失败、连接、操作结果四类状态都没有可信的常驻表达；其中 30 秒自动下载 JSON 是当前唯一的自动「保存」可见行为，属于 P0。
2. **390×844 下画布 34×18，不是「移动端体验差」，而是「没有移动端策略」。** 本轮应明确承诺「桌面优先、窄屏可用（≥360px）」，不做完整移动端。
3. **可访问性最低成本的三件事：** `<html lang="zh-CN">`、图层操作 24×24 命中区、图层行键盘可达。三项都是 S，且不影响现有架构。
4. **中英混用必须本轮统一 9 个点**（8 处文案/标签 + `lang` 声明）：`Untitled`、`Blank … canvas`、`vector`、`AI chat`、`PaintCodex canvas`、`Logs:`、`chats`、`Stroke N`，以及 `<html lang="en">`；其余技术词应保留英文。
5. **监控页的 live 指示可以复用**，画布页连接状态是 S 级修复；不需要新建轮询或离线队列。

**本轮跨领域判定规则（建议冻结）：**

| # | 规则 | 含义 |
|---|---|---|
| R1 | 不可用即禁用 | 无可执行对象的操作不得显示为可用后静默无效 |
| R2 | 状态必须可见 | 保存、连接、错误至少各有一处常驻或可行动表达 |
| R3 | 命中区 ≥24×24 | 图层操作优先 28×28，视觉图标可以更小 |
| R4 | 用户文案中文 | 仅品牌、格式名、监控技术标识在白名单内 |
| R5 | 键盘可见、可完成 | 焦点必须可见；图层管理必须可纯键盘完成 |
| R6 | 不新增板块 | 所有修复复用现有位置与组件，不引入 UI 库 |

### CC-01 保存与操作反馈缺失，30 秒自动下载伪装成「保存」

**严重度:** P0 ｜ **工作量:** M ｜ **置信度:** 0.85

**现场证据**

- `App.tsx` 存在每 30 秒调用 `downloadCanvasJson` 的定时器；新建画布后空闲 33 秒，拦截到 `{ "downloads": 1, "name": "Untitled" }`。
- 全仓 Markdown 中无 `auto-save` / `自动保存` / `30 秒` 的设计依据；该行为没有 ADR 或票据支持，属于实现遗留。
- 没有「保存中 / 已保存 / 保存失败」状态。`saving` 只用于禁用撤销、重做、删除（`canvas-store.ts`），用户看不到。
- 失败只出现在顶栏 `.menu-status`：12px、`#e07a7a`、右侧；`error` 直到下一次 mutation 才清空，可能长期停留或突然消失。
- 删除与 AI 生成没有结果条；隐藏只有 `●/○` 变化、没有文字确认；导出成功也无反馈，失败同样只进 12px 红字。
- 状态栏同时硬编码 `缩放: 100%`（真实约 44.8%，见 `02-canvas-brush.md`），说明状态栏尚未被视为可信状态源。
- 保存失败时，画笔路径在 `CanvasStage` 的 catch 中被 `canvas.remove(path)` 移除——用户看到笔画消失，但没有任何解释。

**用户影响（假设，无访谈）**

用户无法判断「我的画是否安全」：自动下载会被理解为保存，或者反过来让人以为每次都要下载文件；真正保存失败时，12px 红字在右上角，容易错过，而笔画直接消失会直接造成「作品丢了」的判断。删除/AI 生成没有结果条，用户需要自己检查图层面板才能确认操作是否生效。

**建议**

1. **删除 30 秒自动下载。** 持久化由 daemon 逐次写入承担；导出是显式备份动作，不应自动触发下载。
2. **状态栏左侧建立唯一保存状态：** `保存中…` / `已保存 · 刚刚` / `已保存 · 12 秒前` / `保存失败 · 重试`。连续笔画用 ≤500ms 防抖，避免每笔闪烁。
3. **操作结果统一为「一行状态 + 撤销」**，不做右上角 toast 堆叠，不遮挡画布：
   - `已删除图层「笔迹 4」 · 撤销`
   - `已添加图层「AI — 红色圆形」 · 撤销`
   - `已导出 PNG`（JSON 建议标注「备份」语义，具体归 05）
   - **撤销必须绑定操作时的 revision**：后续任何 mutation 发生后，结果条不再承诺「撤销该操作」，按钮失效或收起。否则全局快照撤销会撤掉用户后来的笔画，而不是这次删除。
4. **画布级错误改为画布区顶部 `role="alert"` 横幅**，包含具体原因与「重试」；顶栏只保留短状态或移除红字。
5. **保存失败不得静默回滚。** 优先保留笔画，并在保存状态中标明「1 笔未保存 / 重试」；若工程上不可行，至少显示「这一笔未保存」并提供重试，而不是无声移除。
6. **保留原生 `confirm` 删除确认**，删除后再给撤销入口；下一轮再评估「有撤销后是否还需要 confirm」。

**验收标准**

- [ ] 新建画布后空闲 30 分钟，浏览器下载次数为 0，不再出现 `Untitled.json`。
- [ ] 成功画一笔后 ≤1 秒，状态栏出现「已保存」；连续画 5 笔不出现闪烁抖动。
- [ ] 停止 daemon 后画一笔：≤2 秒出现可读错误（`role="alert"`）与「重试」；笔画不被静默移除，或明确显示「未保存」并保留。
- [ ] 删除图层后出现「已删除 · 撤销」，至少 5 秒内可点击，撤销后图层恢复。
- [ ] 若结果条存续期间发生新的绘制/隐藏等 mutation，结果条不再承诺「撤销该删除」（按钮失效或收起），避免撤错对象。
- [ ] AI 生成成功后出现「已添加图层 · 撤销」；失败错误包含重试动作。
- [ ] 导出成功与失败都有可见反馈，且不只存在于顶栏 12px 文本。
- [ ] 同一时刻最多一条操作结果条；不遮挡画布中心区域。
- [ ] 错误在问题解决或用户关闭前保持可见；下一次成功操作可以清除它，但无关操作不得静默清除。

**边界与依赖:** 自动下载的实现票据归 `05`；本文件定义「反馈模型、优先级与呈现位置」。保存失败保留笔画的可行性需工程确认（见 §9）。

### CC-02 图层操作命中区过小，且图标语义弱

**严重度:** P1 ｜ **工作量:** S ｜ **置信度:** 0.90

**现场证据**

- 图层可见性按钮 **7×11 px**，删除按钮 **16×16 px**（`03-layers.md` 实测）。
- 工具按钮约 39×36 px，菜单按钮高 32 px——满足 WCAG 2.5.8 的 24×24 最低线，但仍低于常见 44×44 触控建议。
- 可见性状态用 `●` / `○` 表示（`LayerPanel.tsx`），不是常见的眼睛图标；视觉上更像「圆点状态」。
- 图层行 `padding: 8px 10px`、按钮 `padding: 0`（`layer-panel.css`），点击区域几乎等于字形。
- 同类风险（需复测）：聊天「清空/撤销」按钮仅 `padding: 4px 2px`、字号 12，命中高度可能低于 24；本项按 R3 一并处理。

**用户影响（假设，无访谈）**

隐藏图层是高频操作，7×11 的命中区在触控板、高 DPI 屏幕或手抖时很容易点空；误点删除会弹出确认框，虽然可取消，但打断节奏。`●/○` 需要用户学习才能理解，和「删除 ×」并排时更容易误判。

**建议**

- 所有图层内按钮命中区 **≥24×24**，建议可见性 28×28、删除 24×24；图层行高保持 36–40px，不靠放大字形实现。
- 图标改为可识别的眼睛/眼睛斜杠（内联 SVG），或保留圆点但在 hover/focus 时显示文字提示；删除保留 `×`。
- 相邻按钮之间至少 4px 间距，命中区不重叠。
- 窄屏/触控布局下，主要操作提升到 40×40；桌面保持紧凑。

**验收标准**

- [ ] 画布页所有可点击控件的计算包围盒 ≥24×24（隐藏元素除外）；含图层、菜单、聊天「清空/撤销」、发送/取消。
- [ ] 可见性按钮 ≥28×28，删除按钮 ≥24×24；相邻命中区不重叠、间距 ≥4px。
- [ ] 图层行高 ≤44px，不因放大按钮导致列表明显变长。
- [ ] 200% 缩放下按钮不被裁切、不与文字重叠。
- [ ] 可见性状态有可识别的图形或文本，不再只依赖 `●/○`。

### CC-03 SSE 连接状态不可见，断线后画布静默过期

**严重度:** P1 ｜ **工作量:** S ｜ **置信度:** 0.85

**现场证据**

- `paint-sse.ts` 定义了 `onError`，但 `App.tsx` 的 `subscribeToCanvas` 只传了 `onOpen` 与 `onSnapshotChanged`。
- 画布页没有任何「已连接 / 同步中 / 离线」指示；状态栏只有尺寸、缩放、工具。
- 多标签同步本身正常：第二标签画线，1.2 秒内第一标签从 8 层变 9 层（`03-layers.md`）。
- 监控页已有完整状态与视觉：`实时中` / `重新连接中…` / `连接中…`，含 7px 圆点与颜色（`MonitorPage.tsx`、`monitor.css`）。

**用户影响（假设，无访谈）**

分屏/多标签用户会把画布当成实时协作界面；daemon 重启或 SSE 断开后，其他标签的修改不再出现，但界面毫无变化。用户可能继续在过期画布上作画，直到刷新才发现差异，从而怀疑「数据丢了」。恢复后也没有「已重新同步」的确认。

**建议（最小方案）**

- 在 `App` 维护 `connection: 'connecting' | 'live' | 'reconnecting'`：`onOpen → live`，`onError → reconnecting`。
- 状态栏右侧放小圆点 + 短文案，复用监控页的视觉与文案；窄屏只显示圆点，用 `title` 与 `aria-label` 补全。
- 断线用中性琥珀色，不要用红色错误横幅——因为 EventSource 会自动重连，且用户本地修改仍会尝试保存。
- 恢复时已有 `onOpen → refreshCanvas`，无需新增轮询；在恢复后确认画布已刷新一次即可。
- 不提供手动「重连」按钮，不做离线队列。

**验收标准**

- [ ] 打开画布 ≤1 秒显示「连接中…」，连上后变「实时中」。
- [ ] 停止 daemon 后 ≤3 秒变为「重新连接中…」，且读屏只播报一次状态变化。
- [ ] 重启 daemon 后 ≤5 秒回到「实时中」，并自动刷新一次；期间其他标签新增的图层无需手动刷新即可出现。
- [ ] 网络面板不出现新增轮询请求，只有 EventSource 自身重连。
- [ ] 状态指示在 390 宽度下不溢出，且可被键盘/读屏获取。
- [ ] 断线提示不阻挡画布操作，不改变当前工具。

**边界:** 连接恢复后的数据一致性由全量快照刷新保证（ADR-0004），本项不改变同步协议。

### CC-04 布局无断点承诺：窄屏画布 34×18，多图层挤压 AI 对话

**严重度:** P1 ｜ **工作量:** M ｜ **置信度:** 0.80

**现场证据**

390×844：

```json
{
  "viewport": [390, 844],
  "bodyScroll": [440, 844],
  "workspace": { "w": 439.92, "h": 772, "scrollW": 440 },
  "canvas": { "x": 81, "y": 393, "w": 34, "h": 18 },
  "sidePanel": { "x": 140, "w": 300 }
}
```

- 页面横向溢出 50px；菜单项延伸到 x=424，超出视口。
- 画布显示 **34×18 px**，无法绘画；侧栏固定 300px，工具条 56px。
- `app.css` 使用固定栅格 `56px minmax(0, 1fr) 300px`，`app.css` / `toolbox.css` / `layer-panel.css` / `ai-chat.css` 均无媒体查询；只有 `monitor.css` 有 1100px / 640px 断点。
- 高度方向同样没有策略：1264×625 + 8 图层时，侧栏 `scrollH 595 > 556.75`，AI 对话被压到 186.75px，底部 600.75 已接近工作区底部约 597。

**本轮决策：桌面优先、窄屏可用（≥360px），不做完整移动端。**

依据：

1. 运行前提是本地 daemon + Codex CLI（README 快速开始要求 Node 22、pnpm、Codex CLI 登录），手机默认访问不到 `127.0.0.1`，Phase 1 没有远程访问设计。
2. spec 与 ADR 中没有移动端验收项；Phase 1 明确排除 Electron，也没有触控手势、双指缩放的设计输入。
3. 390 下画布 34×18 说明当前不是「移动端体验差」，而是「完全没有窄屏策略」。本轮把它从「不可用」修到「可用」，完整移动端留到有真实移动使用证据时。

「窄屏可用」的定义：能建画布、画一笔、看图层、开关图层、发 AI 消息、导出；**不要求**触控手势、双指缩放、移动端专用工具栏、横竖屏专门布局。

**建议**

- 断点建议（供工程评估）：
  - `≤1100px`：侧栏 `clamp(260px, 24vw, 320px)`，工具条 48px。
  - `≤860px`：侧栏改为覆盖式抽屉（宽 `min(320px, 86vw)`），画布区始终占满剩余宽度；菜单栏允许换行，隐藏文档名。
  - `≤560px`：抽屉接近全宽；导出项进入第二行；状态栏允许换行或隐藏次要项。
- 画布区设最小可用尺寸保护（≥280px 宽）；在抽屉覆盖时画布不被压缩，而不是继续缩小。
- 侧栏高度改为分区：图层列表独立滚动（`max-height: 45%`），AI 对话 `min-height: 220px`；不再让整个侧栏滚动。
- 菜单栏在窄屏用「换行 + 隐藏次要信息」，不引入下拉菜单组件。
- 不改监控页布局（已有 1100/640 断点）。

**验收标准**

- [ ] 390×844：`document.documentElement.scrollWidth === 390`，无横向滚动。
- [ ] 360×800 与 390×844 同等通过（允许菜单换行更多）；承诺下限是 360，低于 360 不作为验收项。
- [ ] 390×844：画布显示宽 ≥340px、高 ≥190px；能完成「建画布 → 画一笔 → 撤销 → 导出」，刷新后笔画仍在。
- [ ] 390×844：侧栏默认收起，可通过 ≥24×24 的按钮打开；打开后可按 Esc 关闭，焦点返回触发按钮。
- [ ] 390×844：菜单栏所有控件完整落在视口内（`x + width ≤ innerWidth`），状态栏不裁切。
- [ ] 768×1024 与 1024×768：无横向溢出；画布分别 ≥360px 与 ≥520px。
- [ ] 1264×625 + 12 图层：AI 输入框可见且可聚焦，无需滚动整个侧栏；图层列表独立滚动。
- [ ] 抽屉打开时不遮挡「当前正在编辑」的输入框；软键盘场景不作为本轮验收项（未测）。

**重开条件:** 出现局域网/手机访问需求，或真实移动端使用数据；届时重新评估是否升级为完整移动端。

### CC-05 图层行不可键盘选中，键盘用户只能 Tab 到「删除」

**严重度:** P1 ｜ **工作量:** S ｜ **置信度:** 0.85

**现场证据**

- 图层行是 `<li onClick>`，`tabIndex=-1`、无 `role`、无键盘处理（`LayerPanel.tsx`）。
- 可访问性树：`listitem "● Stroke 1 vector ×" [clickable]`，内部只有「隐藏」与「删除」两个按钮可 Tab 到达。
- 当前图层只通过边框/背景色表示（`layer-item--active`），画布上没有对应轮廓。
- 删除按钮是 Tab 序列里第一个可执行动作之一——键盘用户容易在未选中图层的情况下直接触发删除确认。

**用户影响（假设，无访谈）**

键盘用户无法选择图层，也就无法确认「当前图层」是谁；只能靠 Tab 到删除按钮，用 `aria-label` 里的图层名反推。对依赖键盘的用户，图层管理等于不可用；对普通用户，也损失了一条高效路径。

**建议**

- 让「选择图层」成为一个真正可聚焦的控件：行主体用 `<button>`（名称 + 类型），可见性与删除作为兄弟按钮；或使用 roving tabindex + 方向键。
- 键盘行为：`Tab` 进入当前行；`↑/↓` 移动选中；`Home/End` 到首尾；`Enter/Space` 选中。
- 选中状态同时有视觉与 `aria-current` / `aria-selected` 表达。
- 删除与可见性按钮保留在 Tab 序列中，顺序稳定（选择 → 可见性 → 删除）。
- 明确接受：**绘画本身仍需指针设备**；本轮键盘路径覆盖建画布后的图层管理、AI 对话、导出。

**验收标准**

- [ ] 从工具箱按 Tab 可进入图层行并选中，不再跳过行主体。
- [ ] `↑/↓` 在图层间移动选中，`Home/End` 到首尾；选中项有可见高亮。
- [ ] `Enter/Space` 选中图层；读屏播报「笔迹 3，矢量，已选中」。
- [ ] 可见性与删除仍可键盘到达并操作；删除有确认。
- [ ] 焦点环在选中行上不被蓝色边框覆盖。
- [ ] 纯键盘可完成：新建画布 → 选择图层 → 隐藏 → 显示 → 删除 → 撤销（绘画除外）。
- [ ] 鼠标点击行为不回归。

### CC-08 屏幕阅读器语义：输入框无标签、流式朗读、toggle 语义混用

**严重度:** P2 ｜ **工作量:** S/M ｜ **置信度:** 0.75

**现场证据**

- AI 输入框只有 `placeholder="描述你想画的内容…"`，无 `<label>`、无 `aria-label`（`AiChatPanel.tsx`）。
- 消息容器 `aria-live="polite"`；流式 `delta` 会不断改写文本，可能逐段朗读长回复（`07-cross-cutting.md`）。
- 可见性按钮 `aria-label="隐藏/显示 Stroke 1"` + `aria-pressed` 同时表达动作与状态，读屏会读成「显示 Stroke 1，切换按钮，未按下」。
- 画布 `aria-label="PaintCodex canvas"` 是英文，且画布不可聚焦、无键盘绘画替代。
- 删除使用原生 `window.confirm`，读屏可读，这是优点，应保留。

**用户影响（假设，无访谈）**

读屏用户进入 AI 面板时不知道输入框是什么；发送长回复时会被反复朗读打断；可见性按钮的「动作 + 状态」组合会产生歧义，无法确认当前是显示还是隐藏。

**建议**

- 给输入框加可见或视觉隐藏的 `<label>`（「描述你想画的内容」），placeholder 只作示例。
- 可见性按钮使用**固定标签 + 状态**：`aria-label={`${layer.name} 可见性`}` + `aria-pressed={visible}`；或只用状态标签（「笔迹 1，可见 / 已隐藏」），二选一，不混用。
- 流式朗读：把增量文本放在 `aria-hidden` 区域，另设 `role="status"` 的 live region，只在「步骤变化」与「最终回复完成」时更新；避免 token 级朗读。
- 画布 `aria-label` 改为中文，并说明「画布内容，图层列表提供可访问替代」；不承诺键盘绘画。
- 原生确认框保留。

**验收标准**

- [ ] 读屏聚焦输入框时播报名称「描述你想画的内容」，而不是只读 placeholder。
- [ ] 发送一条长回复：朗读次数 ≤ 1 次用户消息 + 步骤变化次数 + 1 次最终回复；不逐段朗读。
- [ ] 可见性按钮播报稳定的图层名 + 当前状态，且状态变化只播报一次。
- [ ] 画布 aria-label 为中文，且不与图层列表重复朗读。
- [ ] 删除确认框仍可被读屏识别并操作。

**拆分:** 标签与 `aria-pressed` 属于 S，本轮可做；流式 live region 需要与 `04-ai-chat.md` 一起改，工作量 M，可后续。

### CC-09 缺全局 `:focus-visible`，深色背景下焦点不可辨

**严重度:** P2 ｜ **工作量:** S ｜ **置信度:** 0.85

**现场证据**

- 只有 `monitor.css` 为 `select` 和日志行定义了 `:focus-visible`；画布页没有任何全局焦点样式。

**用户影响（假设，无访谈）**

**验收标准**

- [ ] 从菜单栏 Tab 到状态栏，每个可聚焦控件都有 ≥2px 可见焦点环。
- [ ] 焦点环与相邻背景对比 ≥3:1。
- [ ] 焦点环在侧栏滚动容器内不被裁切。
- [ ] 鼠标点击按钮不出现焦点环；键盘操作出现。
- [ ] 监控页与画布页焦点视觉一致。

## 7. 建议实施顺序

| 阶段 | 内容 | 出口条件（Gate） | 依赖 |
|---|---|---|---|
| **0. 决策冻结** | 确认「桌面优先、窄屏可用」；确认状态栏承载保存/连接；确认英文白名单；确认默认画布名中文化 | 四条决策写进 spec 或 ADR 备注，工程据此评估 | 产品 + 工程 |
| **1. 止血（A）** | CC-01a、CC-06、CC-02、CC-07、CC-09 | 无自动下载；无可见英文；命中区 ≥24；对比度与焦点脚本通过 | 无 |
| **2. 状态可见（B）** | CC-01b、CC-03 | 断 daemon、删除图层、AI 成功、导出失败四条脚本通过；状态栏不溢出 | A 的状态栏布局 |
| **3. 布局韧性（C）** | CC-04 | 390/768/1024/1264 四视口 + 12 图层脚本通过 | B 确定状态栏信息优先级 |
| **4. 键盘/读屏（D）** | CC-05、CC-08a | 纯键盘图层管理脚本 + 读屏手工脚本通过 | C 的抽屉焦点返回 |
| **5. 收口（E）** | CC-10 | 同类控件唯一值；R1 审计通过；与 `screenshots-baseline-01.png` 对比无意外回归 | A–D 合并后执行，避免返工 |

**排序理由：**

- A 全是低风险、可独立回滚的改动，先做能立即提升质量，也给后续改动建立「状态/文案/尺寸」基线。
- B 建立状态承载位置；C 会改状态栏与侧栏布局，必须在 B 之后，避免两次调整同一区域。
- D 依赖 C 的抽屉焦点管理；E 最后做，避免在样式反复变动时重复对齐。

## 8. 开放问题 / 假设

### 8.1 假设（无访谈/无数据）

1. **用户主要在桌面本地使用。** 依据是 README 的运行前提（Node、pnpm、Codex CLI、`127.0.0.1`），不是用户数据。若假设错误，CC-04 的范围需要重开。
2. **用户会开多个标签页。** 无行为数据；CC-03 的价值建立在这个假设上。若多标签很少，连接状态可降级为「仅断线时提示」。
3. **中文是唯一 UI 语言。** 依据是现有文案与团队沟通语言；若计划英文版，CC-06 应改为 i18n 立项，而不是硬编码中文。
4. **30 秒自动下载不是需求。** 全仓无 ADR/票据/文档依据；若有未记录的「自动备份」需求，应改为可关闭的显式备份，而不是静默下载。
5. **删除确认可以保留原生 `confirm`。** 无用户反馈；它可读、可取消，本轮不替换。

### 8.2 待决策

1. **响应式承诺的正式措辞：** 建议写入 spec 的 Non-goals：「Phase 1 桌面优先，窄屏 ≥360px 可用；完整移动端不在范围」。需要主 agent/产品确认。若主 agent 决定本轮承诺完整移动端，CC-04 从 M 升级为 L，并需补充触控、软键盘、横竖屏验收。
2. **WCAG 目标等级：** 本轮按 AA 的关键项（对比度、命中区、键盘、语言）做，不承诺全站合规。是否有客户/合规要求？
3. **英文白名单由谁拍板：** 建议产品 + 工程共同确认；监控技术词保留，`Logs:`/`chats` 必须中文。
4. **默认画布名改中文的契约影响：** daemon `service.ts` 默认值、`canvas.test.ts` 断言、导出文件名、旧画布兼容性，需要工程确认后再改。
5. **删除确认与撤销的关系：** 有撤销后是否移除 `confirm`？本轮保留，下一轮用数据/反馈决定。
6. **状态栏信息优先级：** 建议「保存 > 连接 > 工具 > 尺寸/缩放」；`02` 修真实缩放后，窄屏是否隐藏缩放需要设计确认。
7. **触控设备占比：** 决定 CC-02 做到 24 还是 44；当前证据不足以判断。
8. **AI 对话与连接状态的关系：** 聊天流是独立 `fetch`，SSE 断开不影响进行中的回复；状态文案不应暗示「AI 已断开」。需要与 `04` 对齐措辞。
