**严重度定义（本文件及同批审计共用）**

- **P0** — 反馈/数据本身是错的，或主流程被阻断且界面没有出路。本轮必须修。
- **P1** — 主流程能走通，但显著损害用户信心或效率；已有低成本修法。本轮应修。
- **P2** — 打磨项，不影响任务完成；可本轮末或下轮。
- **工作量** — S ≤ 0.5 天，M 1–2 天，L > 3 天（单人，含测试）。不含协议变更的联调成本时另注。

**先确认的既有优点（不要在本轮弄丢）**

- 取消后输入框与按钮正确恢复，`已取消` 有独立样式，不污染回复正文。
- 错误使用 `role="alert"`，超时文案已做机器文本 → 用户文案的映射。
- 助手消息容器有 `aria-busy`，阶段行有独立视觉层级。
- 监控页有完整的 live 状态（连接中 / 实时中 / 重新连接中 / 已暂停）与 trace 面板。

## 2. 体验路径摘要（现场）

1. **成功链路**：输入「画一个红色圆形」→ 用户消息立即出现 → 助手气泡显示 `AI 正在思考…`（后端 `codex_exec` 阶段文案，源码兜底为 `思考中…`），输入框禁用、按钮变「取消」→ **约 19–20 秒**后图层列表出现 `AI — 红色圆形`（`✦ AI`），助手最终文本 `好的，我给你画一个红色圆形。` → 工具栏撤销变为可用。完成后 DOM 中 `steps: []`，阶段行消失。
2. **取消链路**：输入「画一座山」→ 1.2 秒后点「取消」→ 气泡显示 `已取消`，按钮恢复「发送」，输入框恢复可用，无新图层。监控把这次记成 `chat_completed` 的 `warn` + `aborted: true`。
3. **刷新**：URL / localStorage 恢复 `canvasId`，AI 图层保留；对话历史清空，草稿丢失。
4. **无画布聊天**：发送「你好」可正常回复并建议“在画布上添加一层新的矢量图形”，界面没有任何“无画布”前置提示。
5. **监控**：5 分钟窗口显示 `错误率 0.0%` + hint `1 个错误`、`AI 成功率 0.0% 0 / 1 chats`；日志固定 200 条、`200 of 200`。
6. **连接**：画布页无任何连接指示；`subscribeToCanvas` 的 `onError` 在 `App.tsx` 中未传入（代码推导，非现场）。

## 3. 发现列表

### AI-01 20 秒等待只有一行“思考中”，没有时间感与阶段可读性

- **严重度:** P1
- **现场证据:** 发送到图层出现约 19–20 秒（`04-ai-chat.md`）；期间界面只有 `AI 正在思考…`；完成后 `steps: []`。源码 `AiChatPanel.tsx` 只保存 `currentStep` 单值、`finally` 中清空；后端 `AI_CHAT_STEPS` 有 4 个阶段，但 `prompt_built` / `action_parse` / `action_apply` 都在毫秒级，真正占满 19 秒的是 `codex_exec`。另外流式 `delta` 到达后阶段行仍停在「AI 正在思考…」，与已经在输出文字的事实不一致。
- **用户影响（假设，置信度 中）:** 20 秒内没有“还在动”的证据，用户无法区分“在工作”和“卡死”，倾向于取消（→ AI-03 的取消率被抬高），或重复发送导致重复图层。
- **建议:**
  1. 前端本地计时：助手气泡内显示 `已用 12s`，每秒更新（不新增网络请求）。
  2. 阶段行在 `delta` 开始到达时切换为「正在生成…」，让文案跟事实一致。
  3. 完成后不再清空为空白，保留一行终态：`已完成 · 用时 19s`（失败/取消同理保留用时）。
  4. 阶段列表暂不做逐条勾选；单行阶段 + 计时已足够，避免在 280px 高的消息区堆 UI。
- **验收标准:**
  - [ ] Given 发送成功请求，when 请求进行中，then 气泡显示当前阶段文案与每秒更新的已用秒数（刷新间隔 ≤ 1s，页面隐藏时允许暂停）。
  - [ ] Given 首个 `delta` 到达，then 阶段文案变为「正在生成…」。
  - [ ] Given 请求完成，then 阶段行变为终态（`已完成 · 用时 Ns`）且计时器停止，不再出现空阶段。
  - [ ] Given 取消或失败，then 终态显示对应文案与用时。
  - [ ] 上述改动不新增后端请求，`aria-busy` 行为不变。
- **工作量:** S
- **置信度:** 高（行为与源码一致，改动边界清楚）；用户价值为中（无访谈）。

### AI-02 生成成功后没有“已添加图层 / 可撤销”的落地确认

- **严重度:** P1
- **现场证据:** 成功链路中图层出现在列表、撤销可用，但对话只说 `好的，我给你画一个红色圆形。`，没有系统级确认（`04-ai-chat.md`）。**后端已经发送 `layerCreated: { id, name }`**（`routes.ai.ts`），协议也已定义（`packages/protocol/src/index.ts` 的 `StreamPayload.layerCreated`），但 `AiChatPanel.handleFrame` 完全没有消费它。
- **用户影响（假设，置信度 高）:** 画布可视区域之外或图层列表被挤压时（8 图层时聊天区仅 186.75px），用户不知道画布已变化，可能再次提示 AI，产生重复图层；也不知道这一步可以撤销。
- **建议:** 消费已有的 `layerCreated`，在助手气泡下追加一条系统状态行：`已添加图层「AI — 红色圆形」`。仅在“该图层仍是最后一步操作”时提供可点击的「撤销上一步」，调用现有 `store.undo()`；若用户之后又画了一笔，则降级为纯文本 `可在图层面板删除`。
  - **取舍:** 直接给「撤销」按钮更顺手，但快照撤销是“撤销最后一步”（ADR-0003），用户先画一笔再点会撤掉自己的笔画。必须用 revision 守卫，不能只给一个无条件按钮。
- **验收标准:**
  - [ ] Given AI 成功创建图层，then 气泡内出现包含图层名的确认行（不依赖 AI 回复文本）。
  - [ ] Given 确认行出现后用户未做新操作，when 点击「撤销上一步」，then 该 AI 图层消失，确认行变为「已撤销」。
  - [ ] Given 确认行出现后用户又产生了新的画布操作，then 撤销入口不可点击或已隐藏，不出现“撤销错对象”。
  - [ ] Given 请求失败或无图层创建（含无画布），then 不出现确认行。
- **工作量:** S（状态行 + revision 守卫）
- **置信度:** 高（协议字段已存在，属“接通已有能力”而非新功能）。

### AI-03 主动取消被算作“AI 失败”，成功率的语义是错的

- **严重度:** P1
- **现场证据:** 1.2 秒取消后界面显示 `已取消`，行为完全正常（`04-ai-chat.md`）。监控中该次记为 `chat_completed` + `level: warn` + `aborted: true`；`repository.ts` 的 AI 成功率只把 `level='info'` 记为成功，于是 `0 / 1 chats = 0.0%`（`06-monitor.md`）。窗口内唯一一次 chat 就是这次取消，先前成功的已滑出 5 分钟窗口。
- **用户影响（假设，置信度 中高）:** 对开发者/产品是误导性信号——主动取消是用户意图，不是模型失败；把它算进分母会让“AI 成功率”在任何有人取消的窗口里系统性偏低，进而误导 Codex prompt/超时策略的判断。
- **建议:**
  1. **产品判断：取消不算失败。** 从成功率分母中剔除 `aborted: true` 的记录，并单列「取消」计数；日志仍保留 `warn`（表示未完成，便于调试），但 UI 不把它画成错误。
  2. 成功率 hint 改为 `1 / 1 chats · 1 取消`，让两个信号同时可见。
  3. 与 MON-02 一起落地（同一口径、同一协议字段）。
- **验收标准:**
  - [ ] Given 1 次成功 + 1 次取消，then 成功率为 `100.0%`（1/1），hint 显示 `1 取消`。
  - [ ] Given 只有 1 次取消，then 不显示 `0.0%` 作为成功率（见 MON-02 小样本规则）。
  - [ ] Given 真实失败（`level=error`），then 仍计入分母且不计成功。
  - [ ] 日志仍保留 `aborted: true` 与 `warn` 级别，trace 可查。
- **工作量:** S（SQL 增加 `aborted` 判定 + `MonitorStats` 增字段 + 前端 hint）
- **置信度:** 高（语义判断）；口径阈值（是否 0 次成功也显示 0%）待产品确认。

### AI-04 无画布时仍可聊天，用户被引导到一次注定失败的“作画”

- **严重度:** P1
- **现场证据:** 无画布发送「你好」，AI 正常回复并主动建议“让我在画布上添加一层新的矢量图形”（`01-first-run.md`）；此时没有画布承载。后端在解析到画布操作且 `canvas` 为空时返回 `canvas_required` / `请先打开画布再让 AI 绘制。`（`routes.ai.ts`，代码推导的错误路径）。
- **用户影响（假设，置信度 中高）:** 新用户最容易先点 AI 面板；AI 自己发出作画邀请却无法兑现，第一次交互就以红色错误收场。
- **建议:** 不禁用聊天（咨询构图/配色是有价值的），但把“模式”说清楚：
  1. 无画布时，在输入框上方显示一行常驻提示：`当前没有画布，AI 只能给建议。` + 「新建画布」按钮。
  2. `canvas_required` 错误里也带「新建画布」动作（而不是纯文本）。
  3. **不采用**“发送时自动建画布”：隐式副作用会让用户不知道画布从哪来，且与 `01-first-run` 的首次引导冲突。
- **验收标准:**
  - [ ] Given 无画布，then 聊天区显示无画布提示与可点击「新建画布」。
  - [ ] Given 点击该按钮，then 创建画布成功，聊天历史与草稿保留（面板不卸载）。
  - [ ] Given 无画布时 AI 返回画布操作，then 错误条包含「新建画布」入口。
  - [ ] Given 有画布，then 无上述提示。
- **工作量:** S
- **置信度:** 高（现场 + 后端错误分支）。

### AI-05 错误不可恢复：没有重试、草稿不回来、空 AI 气泡、网络错误是英文

- **严重度:** P1
- **现场证据:** 错误显示在输入框上方红色 `role="alert"`；超时映射为「请求超时，请重试」；兜底为「AI 助手无法响应。请检查 Codex CLI 是否已安装并已登录。」；**没有重试按钮**，错误发生后草稿不恢复（`04-ai-chat.md`）。源码：`send()` 先 `setInput('')`，catch 里只 `setError`；`userFacingError` 只处理超时，`TypeError: Failed to fetch` 会原样显示；非 2xx 兜底 `AI request failed (${status})` 也是英文；失败后最后一条助手消息内容为空，界面留下一个只有「AI 助手」标签的空气泡（以上三条为代码推导，未现场触发）。
- **用户影响（假设，置信度 中高）:** 错误把用户推回“重新打一遍提示词”的起点；daemon 没启动时用户看到英文技术错误，不知道该开什么；空白气泡让对话历史看起来坏了。
- **建议:**
  1. 错误分类映射到中文可操作文案：网络/daemon 不可达 → `无法连接本地服务，请确认 PaintCodex daemon 正在运行`；超时 → 保留现文案；5xx → `AI 服务暂时不可用`；`canvas_required` → 见 AI-04。原始技术细节放 `title` 或折叠明细，不占主文案。
  2. 错误条内置「重试」：复用最后一条用户消息，**不追加**新的用户消息，复用最后一个空助手气泡。
  3. 失败后若输入框为空，恢复刚发送的草稿；若用户已开始输入新内容，不覆盖。
  4. 失败气泡内标注「未完成」，不要留空白。
  5. 超时文案里的“重试”现在只是文字，必须真的有一个按钮承接。
- **验收标准:**
  - [ ] Given daemon 停止后发送，then 显示中文「无法连接本地服务…」，不出现 `Failed to fetch` / `AI request failed (500)`。
  - [ ] Given 任意失败，then 错误条提供「重试」，点击后复用同一提示、不产生重复用户消息、空助手气泡被复用。
  - [ ] Given 失败且输入框为空，then 草稿恢复为刚才内容；Given 用户已输入新内容，then 不被覆盖。
  - [ ] Given 失败，then 对话中该轮助手消息显示「未完成」，不出现无内容气泡。
  - [ ] Given 超时，then 文案仍为「请求超时，请重试」，且「重试」可点。
- **工作量:** M（需要把 `send` 拆出可复用的 `sendMessage(text)` 并处理消息复用）
- **置信度:** 高（源码路径明确）；错误文案的实际触发未现场采集。

### AI-06 刷新丢对话与草稿，持久化边界没有被定义

- **严重度:** P2
- **现场证据:** 刷新后 AI 图层保留，对话恢复空状态文案，草稿丢失（`04-ai-chat.md`、`05-export-persistence.md`）。切换监控页时工作区保持挂载，对话不丢（`App.tsx` 注释与结构）。Phase 1 数据模型没有会话表；ADR-0006 的 `agent_logs` 是观测数据，不是对话存储。
- **用户影响（假设，置信度 低）:** 误刷新会丢掉正在输入的提示词；但“回看上一轮提示”是否刚需，没有访谈证据。
- **建议:** 明确并写下边界，不引入数据库：
  - **持久化（SQLite）**：画布、图层、快照、revision —— 作品数据。
  - **会话内（内存）**：消息、阶段、计时、错误 —— 切页/折叠保留，刷新即结束。
  - **草稿（sessionStorage，可选 S）**：仅保存未发送文本，防误刷新；不保存消息历史。
  - 不做对话恢复；若未来要做，应作为独立特性重新过机会评估，而不是顺手加表。
  - 可选文案：有画布但对话为空时，空状态补一句 `新会话 · 画布内容已恢复`，避免用户以为对话“丢了”。（是否加，取决于是否造成噪音，见开放问题。）
- **验收标准:**
  - [ ] Given 输入未发送的草稿后刷新，then 草稿恢复（若采纳 sessionStorage）。
  - [ ] Given 刷新，then 不承诺恢复对话历史，界面不出现“正在加载历史”之类暗示。
  - [ ] Given 发送中切换到监控页再返回，then 对话与进行中状态不丢失（现状，需回归保护）。
- **工作量:** S（仅草稿）/ 边界文档 0
- **置信度:** 中（价值未验证，成本低）。

### AI-07 流式输出触发 `aria-live` 连续朗读，输入框没有可访问名称

- **严重度:** P2
- **现场证据:** 消息容器 `aria-live="polite"`（`AiChatPanel.tsx`），每个 `delta` 都会追加文本；`textarea` 只有 placeholder，没有 `<label>`/`aria-label`（`07-cross-cutting.md`）。面板 `aria-label="AI chat"` 仍是英文。
- **用户影响（假设，置信度 中）:** 屏幕阅读器用户会被逐段朗读打断，且可能听不到“完成/失败”这类关键终态；输入框在表单模式下没有名称。
- **建议:** 流式期间把消息区设为 `aria-live="off"`（或仅在非流式时 polite），另设一个视觉隐藏的 `role="status"` 区域，只在阶段变化、完成、失败时播报一次；给 textarea 加 `aria-label="AI 提示词"`；`AI chat` → `AI 对话`。
- **验收标准:**
  - [ ] Given 流式响应，then 屏幕阅读器不会对每个增量播报；阶段变化/完成/失败各播报一次。
  - [ ] Given 聚焦输入框，then 可访问名称为「AI 提示词」。
  - [ ] 面板 region 名称为中文。
- **工作量:** S
- **置信度:** 中（需读屏实测，现场未做）。

### MON-01 错误率 `0.0%` 与 hint `1 个错误` 自相矛盾（同一张卡片）

- **严重度:** P0
- **现场证据:** 5 分钟窗口 `{"错误率":"0.0%","hint":"1 个错误"}`（`06-monitor.md`）。`repository.stats()`：`errorCount` 统计**所有分类**的 `level='error'`；`errorRate = httpFailureCount / requestCount` 只统计 `category='http'` 且 `level in (warn,error)`。两者分子分母都不同，却放在同一张卡里。另：`ratio(0, 0)` 返回 `0`，所以“没有 HTTP 请求”也会显示 `0.0%`，而 `formatPercent` 固定一位小数。
- **用户影响（假设，置信度 高）:** 监控是唯一的可观测界面；它自己互相矛盾时，开发者会得出“没有错误”的结论，直接影响对 AI 失败、Codex 超时的判断。这是数据可信度问题，不是文案洁癖。
- **建议:** 拆清楚口径，不合并成一个“更好看”的数：
  1. 卡片改名为「HTTP 错误率」，hint 改为 `0 失败 / 24 请求`（分子分母都写出来）。
  2. 单独呈现全部错误：`全部错误 1 · ai-chat 1`（可复用现有分类条的 errorCount 汇总），或作为第二张卡片。
  3. 分母为 0 时显示 `—`，不显示 `0.0%`。
  4. 若产品希望“错误率”指全部日志，则应改公式并同步改文案——但本轮建议保留 HTTP 口径，因为分母明确。
- **验收标准:**
  - [ ] Given 1 个 ai-chat error、0 个 HTTP 失败，then 页面不同时出现“0.0%”与“1 个错误”这种无解释的并置；两个数各有明确分母。
  - [ ] Given 窗口内 0 个 HTTP 请求，then HTTP 错误率显示 `—`。
  - [ ] Given 有 HTTP 失败，then 分子/分母与 hint 一致（hint 数字可复算）。
  - [ ] 分类条中的错误计数与“全部错误”总数一致。
- **工作量:** S（前端文案 + `stats()` 返回 `httpFailureCount` 或 hint 组装；不改表结构）
- **置信度:** 高（现场数字 + 源码公式可直接对上）。

### MON-02 AI 成功率用 1 个样本显示 `0.0%`，且不区分取消

- **严重度:** P1
- **现场证据:** `AI 成功率 0.0% · 0 / 1 chats`（`06-monitor.md`）；唯一样本是取消（warn + aborted）。成功的那次已滑出 5 分钟窗口，所以不是统计 bug，而是**展示规则**让 1 个样本看起来像确定结论。`formatPercent` 固定一位小数，没有样本量提示或置信度提示。
- **用户影响（假设，置信度 中高）:** 开发者会把 `0.0%` 当成“AI 完全不可用”，从而错误地调整 prompt/超时；实际只是 1 次主动取消。
- **建议:**
  1. 与 AI-03 同一口径：取消不进分母，单列取消数。
  2. 小样本规则：`n < 5` 时数值显示 `—`，hint 保留 `0 / 1 chats`；`n ≥ 5` 才显示百分比。（阈值 5 是假设，可配置）
  3. hint 同时给出窗口：`最近 5 分钟 · 1/1 chats · 1 取消`。
- **验收标准:**
  - [ ] Given 1 次取消、0 次成功，then 不显示 `0.0%`；显示 `—` 与 `0/0 chats · 1 取消`（或等价文案）。
  - [ ] Given 4 次成功、0 次失败，then 仍显示 `—` 并提示样本不足（n<5）。
  - [ ] Given 5 次成功、0 次失败，then 显示 `100.0%`。
  - [ ] 取消不进入分母的规则在 API 层生效，前端不重复计算。
- **工作量:** S（依赖 AI-03 的字段）
- **置信度:** 高（展示规则）；阈值需产品确认。

### MON-03 日志硬上限 200 条，无分页、无“还有多少”

- **严重度:** P2
- **现场证据:** `LOG_FETCH_LIMIT = 200`；页面显示 `200 条日志已缓存`、列表表头 `200 of 200`（`06-monitor.md`）。但 `LogList` 的 `200 of 200` 是“过滤后 / 缓冲区”，**不是服务器总数**；API 已支持 `limit` / `offset` 并返回 `total`（`repository.query()`），前端没用。若窗口内超过 200 条，更早记录只能靠缩小时间窗口或加过滤条件查看。
- **用户影响（假设，置信度 中）:** 排障时用户会误以为“就这些日志”，或者被迫反复调筛选条件找一个刚发生的错误。
- **建议:** 保留 200 条首屏；表头改为 `已显示 200 / 共 N 条`；加「加载更多」按 `offset` 追加并去重；筛选变化时重置 offset。虚拟滚动不做。
- **验收标准:**
  - [ ] Given 服务端 total > 200，then 界面显示总数，并可通过「加载更多」继续加载直到 total。
  - [ ] 加载更多不产生重复行，排序保持当前规则。
  - [ ] 切换分类/级别/时间窗口后，列表与 offset 重置，不混入旧筛选结果。
  - [ ] 实时新增日志与分页数据不冲突（按 id 去重）。
- **工作量:** S（API 已具备）
- **置信度:** 高。

### MON-04 “已暂停”时统计仍在刷新，暂停语义不完整（代码推导，待现场复核）

- **严重度:** P2
- **现场证据:** `MonitorPage` 中统计刷新是独立 `setInterval(..., 5_000)`，不随 `paused` 停止；`paused` 只影响 `/monitor/events` 订阅与 live 标签（`06-monitor.md` 未覆盖此点，属代码推导）。
- **用户影响（假设，置信度 低）:** 用户点「暂停实时」想冻结画面做对比，但概览数字仍在变，容易误读“暂停无效”。
- **建议:** 二选一并写清楚：暂停时同时冻结统计（更符合“快照排障”心智），或把按钮改名为「暂停日志流」并让统计卡标注“每 5 秒刷新”。推荐前者，成本更低。
- **验收标准:**
  - [ ] Given 点击暂停，then 统计数字在暂停期间不再变化；点击继续后恢复。
  - [ ] 或：暂停按钮文案明确为「暂停日志流」，统计区有独立刷新说明。
- **工作量:** S
- **置信度:** 中（需现场确认暂停时数字是否真的变化）。

### CONN-01 画布 SSE 断线对普通用户完全不可见

- **严重度:** P1
- **现场证据:** 画布页没有连接/同步指示（`07-cross-cutting.md`）；`paint-sse.ts` 提供 `onError`，`App.tsx` 调用 `subscribeToCanvas` 时未传；监控页有完整 live 状态，两套体验不一致。`onOpen` 已有 `refreshCanvas()`，因此重连后能自愈，但断线期间没有任何提示。
- **用户影响（假设，置信度 中高）:** daemon 重启或本地网络抖动时，画布静默不同步；用户继续画，看不到其他标签页的改动；AI 也会失败但错误文案是英文（见 AI-05），两个问题叠加时用户无法定位是“AI 坏了”还是“服务断了”。
- **建议:** 复用监控页的状态词，在状态栏加一个低噪声连接指示：正常时只显示一个小圆点或省略；异常时显示 `实时同步中断，正在重连…`；恢复后短暂显示 `已连接` 并刷新一次。状态文本加 `role="status"`，避免用 `alert` 打断。
- **验收标准:**
  - [ ] Given 停止 daemon，then 5 秒内状态栏出现「实时同步中断，正在重连…」。
  - [ ] Given daemon 恢复，then 指示回到正常态，并触发一次画布刷新（不重复刷新）。
  - [ ] Given 正常连接，then 指示不抢占视觉焦点（不新增常驻大块 UI）。
  - [ ] 断线状态可被屏幕阅读器在状态变化时播报一次。
- **工作量:** S–M
- **置信度:** 高（EventSource 语义 + 未使用的 `onError`）。

## 6. 建议实施顺序

**Phase 0（决策，0.5 天，无代码）**
锁定三件事并写进 spec/ADR 注记：①错误率与成功率的口径及分母；②取消不算失败；③对话持久化边界。口径不定，后面所有 UI 都会返工。

**Phase 1（S，可并行，同一迭代）**
`MON-01` → `AI-02` → `AI-01` → `AI-04`。
理由：都是“接通已有数据/状态 + 文案”，风险低、可独立验收；其中 AI-01/AI-02 都改 `AiChatPanel.tsx`，建议同一 owner 串行提交，减少冲突。

**Phase 2（M，串行）**
`AI-05`（错误状态机与重试）→ `CONN-01`（复用同一套错误/状态文案）。
理由：AI-05 会重构 `send` 的消息复用逻辑，CONN-01 需要同一套“daemon 不可达”文案，先做前者可避免二次改文案。

**Phase 3（S，协议小改）**
`AI-03` + `MON-02`（一次改 protocol + repository + StatsPanel）→ `MON-03` → `AI-07`。

**Phase 4（可选）**
`AI-06` 草稿保留、`MON-04` 暂停语义。取决于 Phase 1–3 的回归情况与剩余预算。

**发布与验证方式（本轮无新功能，走静默发布）**
- 功能开关不必要；按“监控口径”和“对话反馈”两批合入，便于定位回归。
- 验证以现场脚本为主：20 秒成功一次、1.2 秒取消一次、停 daemon 发一次、无画布发一次、刷新一次、200 条以上日志加载更多一次。
- 每批合入后对比 `/monitor/stats` 与页面数字是否可复算。

## 7. 开放问题 / 假设

**必须由工程/父 agent 补充的事实**

1. **真实耗时分布**：请从 `agent_logs` 取最近 50 次 `chat_completed`（`category='ai-chat'`）的 `duration_ms`，给出 P50/P95。用它决定是否需要在 30s/60s 时给“仍在处理，可取消”的提示，而不是凭“20 秒很长”的直觉。
2. **那个 `1 个错误` 的具体 message**：证据只采集了卡片文案，没有采集错误行。需要确认它是 AI 失败、撤销冲突还是别的；不改变 MON-01 的口径结论，但影响错误分类文案的优先级。
3. **`MON-04` 现场复核**：暂停实时后统计卡是否真的继续变化（当前为代码推导）。

**产品假设（无访谈，明确标注）**

4. 假设用户能理解“已用 12s”这类计时；若不能，退化为只显示阶段文案，保留完成后的“用时 Ns”。
5. 假设 20 秒等待已足以让用户焦虑；若 P95 实际 < 8 秒，AI-01 可降为 P2，只保留完成后的用时。
6. 假设监控页的主要读者是开发者（ADR-0006 的定位），因此保留 `http_request`、`chat_completed` 等英文技术词是合理的；中文只覆盖动作与说明。
7. 假设“取消率”是有价值的产品信号；若团队只关心“AI 是否失败”，也可只做剔除、不新增展示（AI-03 的最小版）。
8. 假设草稿丢失的痛感低于对话历史丢失；因此 AI-06 只做 sessionStorage 草稿，不做历史恢复。

**需要与既有决策对齐的点**

9. AI-02 的「撤销上一步」是否违背 ADR-0003 的快照语义？不违背，但必须用 revision 守卫；若工程认为守卫成本高于收益，降级为纯文本提示 + 指向图层面板删除。
10. MON-02 会给 `MonitorStats` 增加 `aiChatCancelledCount` 字段，属于协议增量、非破坏性变更；需确认是否接受在本轮触碰 `packages/protocol`（我认为可以，改动面小于新建模块）。
